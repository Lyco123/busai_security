## 3. 当前部署模式

这台测试服不是“全家桶 compose”模式，而是：

- retrieval 自己起
- Qdrant 由 retrieval 这套 compose 管
- ClickHouse 使用宿主机上已有实例

所以这里必须用：

```bash
docker compose -f docker-compose.server.yml ...
```

不要直接用默认的：

```bash
docker compose ...
```

原因：

- 默认 compose 会尝试再起一个 `kb-clickhouse`
- 这台机器上 `8123` 已被宿主机 ClickHouse 占用
- 你会得到一个端口冲突，然后怀疑人生十分钟

## 4. 当前关键环境信息

### 4.1 ClickHouse

客户提供过的信息里有：

- `CLICKHOUSE_HOST=117.72.212.82`
- `CLICKHOUSE_PORT=9000`
- `CLICKHOUSE_USER=default`
- `CLICKHOUSE_PASSWORD=Zhongda@84`
- `CLICKHOUSE_DATABASE=ai_security`

但对当前 retrieval 实现来说，实际用法是：

- 走 HTTP DSN
- 走宿主机 `8123`
- 当前老表在 `default`

所以最终可用配置应类似：

```env
CK_DSN=http://default:Zhongda%4084@host.docker.internal:8123
```

注意两点：

1. 密码里的 `@` 要编码成 `%40`
2. 当前不要在 DSN 后面带 `/ai_security`，因为历史 KB 表在 `default`

### 4.2 embedding

当前配置使用：

```env
EMBEDDING_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
EMBEDDING_MODEL=text-embedding-v1
EMBEDDING_API_KEY=<实际密钥>
```

如果 `EMBEDDING_API_KEY` 为空，会直接出现：

- 检索 `401`
- worker 无法正常做向量化

### 4.3 Qdrant

当前 retrieval 配的是：

```env
QDRANT_URL=http://qdrant:6333
QDRANT_COLLECTION=kb_clauses_dense
```

启动时可能会看到 client/server 版本不完全兼容的 warning。  
目前它没有阻塞服务启动，但后面最好对齐版本。

## 5. 最常用命令

### 5.1 看容器状态

```bash
cd /srv/bus/retrieval
docker compose -f docker-compose.server.yml ps
```

### 5.2 重建服务

改了 `.env` 或同步了新代码后，使用：

```bash
cd /srv/bus/retrieval
docker compose -f docker-compose.server.yml up -d --build --force-recreate kb-api kb-worker
```

不要只跑：

```bash
docker compose restart
```

因为这不会重新吃 `.env`。

### 5.3 初始化 schema

```bash
docker exec -it kb-api node dist/init-schema.js
```

当前代码里的 `init-schema` 已经包含老 schema 兼容补列逻辑。

### 5.4 看日志

```bash
docker logs --tail=120 kb-api
docker logs --tail=120 kb-worker
docker logs --since=2m kb-api
docker logs --since=2m kb-worker
```

### 5.5 进容器看环境变量

```bash
docker exec -it kb-api /bin/sh -lc 'printenv | grep -E "^EMBEDDING_|^CK_DSN|^QDRANT_URL"'
docker exec -it kb-worker /bin/sh -lc 'printenv | grep -E "^EMBEDDING_|^CK_DSN|^QDRANT_URL"'
```

## 7. 前端和 Worker 侧注意事项

### 7.1 `/kb/*` 当前只给管理员

当前 Worker 代理逻辑是：

- `/api/agent/kb/*`
- 仅管理员可访问

所以如果直接 curl Worker 入口，未带管理员登录态时出现：

```http
403 {"error":"forbidden"}
```

这是预期行为，不是 tunnel 挂了。

### 7.2 前端说“500”，先别信它

前端页面上的“500”有时只是统一错误提示，不一定是真实状态码。

如果前端报错，建议按这个顺序确认：

1. 浏览器 Network 里看真实接口和状态码
2. 直接打 retrieval 域名确认是不是上游本身报错
3. 再打 Worker 入口判断是不是权限或代理层问题

不要只看页面提示词下结论。

## 8. 本地打包和同步方式

### 8.1 本地打包

在 Windows 本地仓库根目录：

```powershell
cd D:\BUS
Compress-Archive -Path agent\retrieval\* -DestinationPath agent\retrieval-latest.zip -Force
```

### 8.2 上传到服务器

```powershell
scp D:\BUS\agent\retrieval-latest.zip root@117.72.212.82:/root/
```

### 8.3 服务器覆盖部署

如果要确保没有旧文件残留，建议直接删目录重解压：

```bash
rm -rf /srv/bus/retrieval
mkdir -p /srv/bus/retrieval
cd /srv/bus/retrieval
unzip -o /root/retrieval-latest.zip
```

### 8.4 覆盖后一定要验证文件内容

不要默认“我上传了，所以服务器就有了”。

至少做一次确认：

```bash
grep -n "ISO_UTC_DATETIME_RE" /srv/bus/retrieval/src/db/clickhouse.ts
```

如果看不到这类新特征代码，说明服务器根本没跑到新版本。

## 9. 已知坑位

这里列的是已经踩过、以后优先排除的坑。

### 9.1 错用默认 compose

症状：

- 试图起 `kb-clickhouse`
- 8123 端口冲突

结论：

- 测试服固定用 `docker-compose.server.yml`

### 9.2 `.env` 改了但容器没更新

症状：

- 配置明明改了
- 行为却完全没变化

结论：

- 不要只 `restart`
- 要 `up -d --force-recreate`

### 9.3 DSN 用了 9000

症状：

- ClickHouse 怎么都不通
- 或者 native 端口能通，但 retrieval 还是报错

结论：

- 当前实现只认 HTTP DSN
- 用 `8123`

### 9.4 老表缺列

症状：

- `order_index` 缺失
- 文件元数据列缺失

结论：

- 跑 `node dist/init-schema.js`
- 再用 `DESCRIBE TABLE` 确认列是否补齐

### 9.5 老 ClickHouse 不接受 ISO UTC 的 `DateTime64`

症状：

- preview / ingest 写入时报 `expires_at` 解析失败

结论：

- 这个坑已经通过代码修复
- 如果再出现，先怀疑服务器没跑到新代码

### 9.6 本地和服务器代码不一致

症状：

- 本地看起来修好了
- 服务器日志却还是老错误

结论：

- 优先检查服务器文件内容
- 不要只看 zip 包时间

## 10. 建议的排查顺序

后面的 agent 如果遇到知识库测试服异常，建议按这个顺序查：

1. `docker compose -f docker-compose.server.yml ps`
2. `curl http://127.0.0.1:8080/health`
3. `curl https://busodemo-kb-api.canocache.com/health`
4. 检查 `kb-api` / `kb-worker` 的环境变量
5. 检查 ClickHouse HTTP 连通性
6. 跑 `node dist/init-schema.js`
7. 直连 retrieval 验证接口
8. 再去看 Worker 代理
9. 最后再看前端

这个顺序不是唯一正确答案，但已经验证过足够省时间。
