# 车辆报告路由 Playwright 手动复测记录

日期：2026-04-09  
测试页面：`https://busodemo.canocache.com/assistant`  
执行方式：Playwright 手动逐轮发送  
测试目标：复测 3 类已知问题，并重新按“实际回复质量”而不是只按执行智能体做分析

## 1. 测试范围

本次只复测以下 3 类问题，共 7 个用例：

1. 双车歧义：2 个用例
2. 不完整输入：2 个用例
3. 多轮信息分散：3 个用例

重点不是单纯看是否进入 `generate_vehicle_report`，而是看：

- 用户是否得到了合理的澄清
- 错误回复是否仍具备可迁移价值
- 问题更像是提示词缺失、提示词太弱，还是实现层承接/校验有问题

## 2. 测试约束

本轮仅允许使用以下两组真实数据：

```json
{
  "numberplate": "粤A02650D",
  "ppartition": "20251221"
}
```

```json
{
  "numberplate": "粤A02013D",
  "ppartition": "20251221"
}
```

执行约束如下：

- 每个用例单独新建会话
- 多轮用例按自然对话顺序逐条发送
- 每发送一条消息后等待约 2 分钟再读取回复
- 对“生成中”的回复额外补等 40 秒左右确认最终落点

## 3. 总结结论

本次复测后，三个问题的严重度排序如下：

1. 多轮补参状态承接，尤其是 JSON 片段补参
2. 双车歧义时的澄清出口
3. 不完整输入的文案和分支细化

原因如下：

- 多轮补参不是单纯“体验略差”，而是会把明确的报告需求打断成“查无此车”或 `vehicle_id` 槽位泄漏。
- 双车歧义有两种失效形态，一种是直接输出坏回复，一种是生成了不该生成的双车合并报告。
- 不完整输入大多数情况下还能给出用户能理解的回复，但“输入不完整”和“查无此车”没有严格区分。

## 5. 逐用例记录

### D1. 双车歧义，用“你先判断一下”

用户输入：

```text
给我生成车辆安全报告，车牌可能是粤A02650D或粤A02013D，分区日期20251221，你先判断一下。
```

预期：

- router 识别到目标车辆不唯一
- 不进入车辆报告生成
- 明确要求用户确认具体车牌，或者确认是否需要双车对比

实际回复：

```text
vehicle_id
```

页面显示：

- `执行Agent: router`

判断：

- 这是最差的一类回复，不是普通误路由，而是内部槽位名直接漏给用户
- 说明系统不是“不会澄清”，而是澄清出口模板或填充链路坏了

结论：

- 这是高优先级缺陷
- 修复后应优先回归

### D2. 双车歧义，不带“先判断一下”

用户输入：

```text
帮我生成车辆安全报告，可能是粤A02650D，也可能是粤A02013D，分区日期20251221。
```

预期：

- 仍应先澄清，因为目标车不唯一

实际回复：

- 先出现“已找到相关数据，正在根据数据生成报告”
- 随后直接生成两辆车的合并报告
- 结构上包括：
  - `已为您生成两辆车辆的画像安全报告（分区日期：20251221）`
  - `车辆一：粤A02650D`
  - `车辆二：粤A02013D`
  - 最后还有联合建议

页面显示：

- `执行Agent: omni`

判断：

- 行为错误：本该澄清，却默认把两个候选都做成报告
- 但正文内容不是废的，整体可读、像样、可用于“用户确认双车都要看”的合法分支

结论：

- 这不是“回复质量差”，而是“触发时机错”
- 建议保留双车汇总能力，但必须放到明确确认之后

### I1. 不完整输入，半截车牌

用户输入：

```text
请生成车辆安全报告，车牌号粤A0265，分区日期20251221。
```

预期：

- 优先告诉用户“车牌不完整，请补全”
- 不应把它说成“没有这辆车”

实际回复：

```text
没有找到与 “粤A0265” 对应的车辆。
当前车辆报告仅支持按车牌查询，请提供准确车牌号。
```

页面显示：

- `执行Agent: router`

判断：

- 用户能看懂，但排障方向被带偏
- 正确语义应是“标识不完整”，不是“查无此车”

结论：

- 这是 lookup 分支命中错误
- 更像实现问题，而不是文案能力不足

### I2. 不完整输入，只有日期

用户输入：

```text
请生成车辆安全报告，分区日期20251221。
```

预期：

- 正常补问缺失的车牌

实际回复：

```text
请提供完整车牌号或车辆ID（例如“A12345”“BUS-102”或“vehicle-001”），我再为你生成车辆安全报告。
```

页面显示：

- `执行Agent: router`

判断：

- 这是合格澄清
- 唯一的问题是口径用了“车牌号或车辆ID”，而其他地方有时用“车牌号或车辆自编号”

结论：

- 这一类不是主故障
- 更适合统一口径，不必作为高优先级 blocker

### M1. 多轮分散，自然语言先车牌后日期

对话过程：

```text
Q1: 我要生成车辆安全报告。
A1: 正在根据车辆相关信息生成安全报告。请提供以下信息，以便生成车辆安全报告：
    车牌号（例如：粤A34049D）
    查询日期（格式：yyyyMMdd，例如：20250401）

Q2: 车牌号粤A02650D。
A2: 没有找到与 “粤A02650D” 对应的车辆。当前车辆报告仅支持按车牌查询，请提供准确车牌号。

Q3: 分区日期20251221。
A3: 已找到相关数据，正在根据数据生成报告。
```

最终页面显示：

- 第三轮最终落到 `执行Agent: generate_vehicle_report`

判断：

- 第一轮澄清正常
- 第二轮明显错，把真实车牌当成“查无此车”
- 第三轮又恢复并成功进报告生成

结论：

- 这不是完全丢状态，而是状态聚合顺序不稳定
- 用户体验非常差，因为中间会收到一次明显误报

### M2. 多轮分散，自然语言先日期后车牌

对话过程：

```text
Q1: 我要生成车辆安全报告。
A1: 正在处理车辆安全报告生成请求。请提供以下信息：
    车牌号
    查询日期

Q2: 分区日期20251221。
A2: 请提供完整车牌号或车辆ID（例如“A12345”“BUS-102”或“vehicle-001”），我再为你生成车辆安全报告。

Q3: 车牌号粤A02013D。
A3: 已找到相关数据，正在根据数据生成报告。
```

最终页面显示：

- 第三轮最终落到 `执行Agent: generate_vehicle_report`

判断：

- 这是三组多轮里最正常的一组
- 说明 pending 澄清能力不是完全失效，而是对补参顺序敏感

结论：

- 当前实现存在“可工作但不稳”的状态
- 这也说明问题重点在承接实现，而不是首轮澄清提示词

### M3. 多轮分散，JSON 片段补参

对话过程：

```text
Q1: 帮我生成车辆安全报告。
A1: 要为您生成车辆安全报告，我需要知道具体是哪一辆车，以及目标画像日期……

Q2: {"numberplate":"粤A02013D"}
A2: 没有找到与 “粤A02013D” 对应的车辆。当前车辆报告仅支持按车牌查询，请提供准确车牌号。

Q3: {"ppartition":"20251221"}
A3: vehicle_id
```

页面显示：

- 第二轮 `执行Agent: router`
- 第三轮仍是 `执行Agent: router`

判断：

- 这是本轮最能说明问题的一组
- JSON 片段没有被视为“继续补参”
- 第二轮被错误改写成一次独立查车
- 第三轮再次退化为槽位泄漏 `vehicle_id`

结论：

- 这不是“提示词略弱”，而是结构化补参承接链路实际失效
- 应作为最高优先级修复对象之一

## 6. 三类问题的重新归纳

### 6.1 双车歧义问题

当前实际有两种子问题：

1. 歧义澄清出口损坏  
表现：直接输出 `vehicle_id`

2. 歧义未被拦截  
表现：默认把两个候选都生成成双车报告

这两个问题不能混为一谈：

- 前者是回复模板/槽位填充链路错误
- 后者是路由约束或二次保险没守住

### 6.2 不完整输入问题

当前也有两种：

1. 缺参澄清正常  
表现：只有日期时会补问车牌

2. 不完整标识被误判为 not_found  
表现：半截车牌被说成“没有找到车辆”

所以“不完整输入”不是整体都坏，而是“半截标识识别”这一支坏得更明显。

### 6.3 多轮信息分散问题

当前可以再拆成三种状态：

1. 自然语言补参可成功，但顺序敏感  
例：先日期后车牌，比先车牌后日期稳定

2. 中途断链但最终自愈  
例：M1 第二轮误报，第三轮恢复

3. JSON 片段补参直接失效  
例：M3 第二轮查无此车，第三轮槽位泄漏

这说明当前最大短板不是“不会问”，而是“问完以后接不稳”。

## 7. 提示词与实现层归因

### 7.1 已有约束并不算弱

`agent/skills/router/SKILL.md`

- 第 127 行明确写了：如果用户同时提到多个可能车辆，或出现“`A或B`”“`可能是A也可能是B`”“`先判断一下`”，不得选择 `generate_vehicle_report`，必须先澄清。
- 第 129 行明确写了：如果当前轮只是 JSON 片段、键值片段或单个槽位回答，应视为继续补参，不要当成新的独立请求。

`agent/src/app/runtime.ts`

- 第 3607-3616 行对 `generate_vehicle_report` 的工具描述也已经写明：
  - 只有明确要求正式车辆报告时才使用
  - 如果用户只是在查车辆信息、基础信息、属性、档案，不得调用
  - 如果用户明确说不要报告，也不得调用

结论：

- 从规则文本看，这两类约束并不缺
- 问题不主要在“没有写”

### 7.2 运行时二次保险不够

`agent/src/app/runtime.ts:3018-3026`

- `validateToolCall` 对 `generate_vehicle_report` 只做了 `vehicle_id` 完整性校验
- 它没有再校验：
  - 当前是不是仍然是正式报告意图
  - 当前目标车是不是唯一
  - 当前是否仍存在 pending 澄清未解决

结论：

- 一旦 router 前面选错了，这里缺少第二道刹车

### 7.3 opening 文案会污染澄清类回复

`agent/src/domains/chat/worker-runner.ts:316-320`

- opening 生成提示里明确要求：
  - 报告生成类请求输出简短开场
  - 优先用类似“已找到相关数据，正在根据数据生成报告”的表达

这会带来一个副作用：

- 哪怕当前其实还在澄清阶段，也容易先挂上一层“正在生成报告”的前缀

这也是为什么一些正文还行的回复，前缀却明显不符合实际状态。

### 7.4 多轮承接实现本身有硬限制

`agent/src/domains/chat/structured-lookup.ts:1545-1555`

- `rewritePendingStructuredLookupFollowUp` 在检测到 `isFreshStructuredLookupRequest(trimmed)` 时会直接返回 `null`
- JSON 片段很容易被当成新的结构化请求，而不是 pending 澄清的继续补参

`agent/src/domains/chat/clarification-state.ts:300-314`

- `buildFillArgs` 只有在 `missing_fields.length === 1` 时才会填参
- 如果一次澄清状态里缺多个字段，它不会在这里完成聚合

这正好解释了本次观察到的现象：

- 自然语言多轮有时还能靠后续状态重组“自愈”
- JSON 片段更容易直接掉出 pending 承接链路

### 7.5 too_short 分支存在，但实测没稳定打中

`agent/src/domains/chat/structured-lookup.ts`

- 第 384 行定义了 `isLikelyIncompleteVehicleArg`
- 第 693-694 行如果命中，会返回 `too_short`

`agent/src/domains/chat/router-service.ts:646`

- 已要求：如果 lookup reason 是 `too_short`，要明确要求用户补充更完整标识

但实际 I1 用例没有表现为 `too_short`，而是走成了 `not_found` 风格回复。

结论：

- 这一类更像实现命中条件或调用路径问题
- 不是因为文案不会写

## 8. 哪些回复可以迁移复用

### 8.1 可直接复用的澄清回复

以下类型可以直接迁到规范澄清链路：

- `请提供完整车牌号或车辆ID，我再为你生成车辆安全报告。`
- `请提供车牌号 + 查询日期。`

这些回复的问题不在内容，而在有时落点不对，或前缀被污染。

### 8.2 可保留但应换触发条件的回复

双车合并报告正文可以保留，但应改成：

- 只在用户明确说“两个都看”“帮我对比两辆车”后触发
- 不能在歧义尚未消解时默认放行

### 8.3 不应复用的回复

以下回复不应继续存在：

- `vehicle_id`
- 半截车牌时的“没有找到该车辆”

前者是槽位泄漏，后者会误导用户。

## 9. 修复优先级建议

### P0

1. 修复 JSON 片段补参承接  
目标：`{"numberplate":"粤A02013D"}` 和 `{"ppartition":"20251221"}` 必须被视为继续补参

2. 修复歧义澄清槽位泄漏  
目标：任何情况下都不能向用户直接输出 `vehicle_id`

### P1

1. 给 `generate_vehicle_report` 增加歧义/意图二次校验  
目标：即便 router 选错，也不要直接放过

2. 修复自然语言多轮的顺序敏感  
目标：M1 不应在第二轮误报查无此车

### P2

1. 区分 `too_short` 和 `not_found`
2. 统一“车牌号 / 车辆ID / 车辆自编号”的对外口径
3. 收敛 opening 前缀，避免在澄清阶段使用“正在生成报告”

## 10. 建议回归用例

修复后建议至少回归以下 7 个用例：

```text
1. 给我生成车辆安全报告，车牌可能是粤A02650D或粤A02013D，分区日期20251221，你先判断一下。
2. 帮我生成车辆安全报告，可能是粤A02650D，也可能是粤A02013D，分区日期20251221。
3. 请生成车辆安全报告，车牌号粤A0265，分区日期20251221。
4. 请生成车辆安全报告，分区日期20251221。
5. 我要生成车辆安全报告。 -> 车牌号粤A02650D。 -> 分区日期20251221。
6. 我要生成车辆安全报告。 -> 分区日期20251221。 -> 车牌号粤A02013D。
7. 帮我生成车辆安全报告。 -> {"numberplate":"粤A02013D"} -> {"ppartition":"20251221"}。
```

验收标准：

- 双车歧义必须先澄清
- JSON 片段必须能续接 pending 补参
- 半截车牌必须提示“不完整”
- 澄清阶段不得出现“已找到相关数据，正在根据数据生成报告”这类已进入生成态的误导前缀
- 不允许再出现 `vehicle_id`

## 11. 最终判断

本轮复测后，可以把问题定性为：

- **不是“router 完全不会澄清”**
- **而是“澄清之后的承接和兜底不稳定”**

更准确地说：

- 双车问题主要是歧义拦截和澄清出口问题
- 不完整问题主要是 `too_short` 分支未稳定命中
- 多轮分散问题主要是 pending 补参承接实现不稳，尤其是 JSON 片段补参几乎失效

因此，后续改造的核心不应只加 prompt，而应同时做：

1. pending 承接链路修正
2. 运行时二次校验
3. opening 文案去污染
