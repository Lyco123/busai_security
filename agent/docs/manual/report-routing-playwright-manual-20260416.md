- **成功召回**：页面显示 `Agent: generate_driver_report` / `generate_vehicle_report` / `generate_unit_report` 等报告生成agent名称。

## 7. 问题分析

### 7.1 "画像风险报告"与"风险总结报告"的差异

从测试结果可以看出明显的规律：

- **"画像风险报告"表述（测试1、3、5、7）**：均路由到 `omni` 或 `router`，未召回报告agent
- **"风险总结报告"表述（测试2、4、6、8）**：驾驶员和车辆成功召回，单位和线路仍失败

这表明：

1. 路由系统对"风险总结报告"的识别优于"画像风险报告"
2. 单位和线路的报告路由存在较大问题，无论哪种表述均未成功

### 7.2 具体失败场景

| 场景                         | Agent       | 分析                                                     |
| ---------------------------- | ----------- | -------------------------------------------------------- |
| 驾驶员画像风险报告           | omni        | 用户意图被识别为咨询而非报告生成                         |
| 车辆画像风险报告（无粤字头） | omni        | 车牌号格式可能影响识别，但"粤A32785D"完整格式成功        |
| 单位报告（两种表述）         | omni        | 单位报告管线路由完全失效                                 |
| 线路报告（两种表述）         | router/omni | 线路报告管线路由完全失效，router表示仅停留在路由决策阶段 |

## 8. 结论

本次测试验证了报告路由系统对四种实体类型的召回能力存在显著差异：

1. **驾驶员报告**：50%召回率，"风险总结报告"表述可成功路由
2. **车辆报告**：50%召回率，完整车牌号+"风险总结报告"表述可成功路由
3. **单位报告**：0%召回率，两种表述均未能路由到报告生成agent
4. **线路报告**：0%召回率，两种表述均未能路由到报告生成agent

**主要发现**：

- 表述方式影响路由："风险总结报告"比"画像风险报告"更容易触发报告管线
- 实体类型影响路由：驾驶员/车辆部分成功，单位/线路完全失败
- 单位和线路的报告生成管线路由需要重点修复
