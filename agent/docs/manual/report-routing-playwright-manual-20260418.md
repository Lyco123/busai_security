## 4. 判定口径

- **成功召回**：`tool` 命中预期报告 agent，例如 `generate_driver_report`、`generate_vehicle_report`、`generate_unit_report`。
- **未召回**：返回 `consult_omni`、`router`、`null` 或其他非目标报告管线。
- **数据未命中但路由正确**：如果落在目标报告 agent，只是报告内容提示"未找到数据"，仍算路由正确。
- **误路由**：落入错误实体的报告 agent。

## 7. 关键发现

### 7.1 驾驶员与单位报告路由稳定

- 驾驶员类：两条测试消息全部命中 `generate_driver_report`
- 单位类：两条测试消息全部命中 `generate_unit_report`

这两类报告对用户提供的自然语言表述有较强的识别能力，路由管线成熟稳定。

### 7.2 车辆类报告对车牌格式敏感

- **ID 3（车辆画像风险报告）失败**：用户输入"车辆（A32785D）"，缺少省份前缀"粤"，系统无法识别完整车牌，返回澄清问句而非进入报告管线
- **ID 4（车辆风险总结报告）成功**：用户输入"粤A32785D"，完整车牌格式，成功路由到 `generate_vehicle_report`

建议：车辆类查询的实体识别规则需对车牌前缀（如"粤"）有明确要求，或在用户输入不完整时自动补全。

### 7.3 线路类报告管线尚未稳定接入

- **ID 7（线路画像风险报告）**：返回 `tool = null`，提示"未找到线路数据"
- **ID 8（线路风险总结报告）**：虽然返回了完整的线路风险汇总正文，但 metadata 显示 `consult_omni`，说明路由层未真正进入线路报告管线

这与之前多轮测试结论一致：线路类目前仍是"结果文案看起来像报告，但路由没有进目标 agent"的状态。

## 9. 结论与建议

### 9.1 现状总结

当前系统报告路由能力呈现明显的分层特征：

| 实体类型 | 路由稳定性 | 主要问题                                           |
| :------- | :--------- | :------------------------------------------------- |
| 驾驶员   | 100% ✓     | 无，表现稳定                                       |
| 单位     | 100% ✓     | 无，表现稳定                                       |
| 车辆     | 50%        | 对车牌格式（省份前缀）敏感                         |
| 线路     | 0%         | 管线未稳定接入，即使返回报告内容也未进入目标 agent |

### 9.2 改进建议

1. **车辆类实体识别优化**：
   - 增加车牌省份前缀自动补全逻辑
   - 或在用户输入不完整车牌时，明确提示需要完整格式（如"粤A32785D"）

2. **线路类报告管线接入**：
   - 排查线路类路由规则是否缺失或不完整
   - 确认线路报告 agent 是否已正确注册到路由层
   - 对已返回线路报告正文但 `tool` 显示 `consult_omni` 的场景，需区分"兜底回复"与"真实 agent 命中"

3. **测试消息措辞统一**：
   - 建议后续测试统一使用标准实体表述格式，减少歧义
   - 车辆类统一使用完整车牌格式（粤AXXXXXX）
   - 线路类统一使用"XX路"或"XX线路"表述
