# 车辆报告生成召回率 Playwright 手动测试记录

日期：2026-04-14  
测试页面：`https://busodemo.canocache.com/assistant`  
执行方式：Playwright 手动逐轮发送  
测试目标：验证车辆报告生成路由召回率，覆盖关键词匹配、近义词表达、语义表达三阶段场景。

## 1. 测试范围与目标

聚焦车辆报告路由的**应召回**与**不应召回**场景，分为三阶段：

- **阶段一**：覆盖近义词、不规范表达、模糊意图等边缘场景
- **阶段二**：使用不同动词复测应召回用例，验证关键词匹配逻辑
- **阶段三**：验证无「车辆」「报告」关键词时的语义表达召回表现

## 2. 数据约束

仅允许使用以下两组数据：

```json
{ "numberplate": "粤A02650D", "ppartition": "20251221" }
```

```json
{ "numberplate": "粤A02013D", "ppartition": "20251221" }
```

## 3. 执行规范

| 项   | 要求                                                |
| ---- | --------------------------------------------------- |
| 会话 | 每例**新建会话**，确保独立测试环境                  |
| 等待 | 每发送一条用户消息后等待约2分钟，确保大模型回复完成 |
| 判定 | 以「执行Agent」字段作为路由判定依据                 |

## 4. 判定口径（召回）

- **应召回（R+）**：用户意图明确为查询车辆状况/安全信息，应路由到 `generate_vehicle_report` 或相关车辆专家智能体。
- **不应召回（R−）**：用户意图与车辆报告无关（天气、购车、违章、保险理赔、价格对比等），不应路由到 `generate_vehicle_report`。

## 12. 关键发现与分析

### 11.1 路由匹配逻辑

通过对比三阶段测试结果，发现：

| 表达类型               | 是否召回  | 原因分析           | 测试阶段 |
| ---------------------- | --------- | ------------------ | -------- |
| 包含「车辆报告」关键词 | ✅ 召回   | 精确匹配触发词     | 阶段二   |
| 包含「生成报告」关键词 | ✅ 召回   | 精确匹配触发词     | 阶段一   |
| 使用近义词「车况报告」 | ❌ 未召回 | 未纳入触发词列表   | 阶段一   |
| 使用近义词「车辆状况」 | ❌ 未召回 | 未纳入触发词列表   | 阶段一   |
| 语义表达「安全情况」   | ❌ 未召回 | 不含关键词触发词   | 阶段三   |
| 语义表达「有什么风险」 | ❌ 未召回 | 不含关键词触发词   | 阶段三   |
| 模糊表达「有问题吗」   | ❌ 未召回 | 无法识别为报告意图 | 阶段一   |

### 11.2 关键词依赖性结论

**核心问题**：系统高度依赖「车辆报告」关键词进行路由。

- 包含关键词：召回率 **100%**
- 不含关键词（近义词/语义表达）：召回率 **14%**

**智能体替代现象**：当表达不包含关键词时，系统倾向于路由到 `vehicle_expert` 或 `omni`。

| 路由目标                | 回复特点                                           | 是否生成正式报告 |
| ----------------------- | -------------------------------------------------- | ---------------- |
| generate_vehicle_report | 结构化「车辆安全风险分析总结报告」，包含标准化章节 | ✅ 是            |
| vehicle_expert          | 提供安全/风险信息，但格式自由，无标准化章节结构    | ❌ 否            |
| omni                    | 提供查询结果或澄清，不生成报告                     | ❌ 否            |

### 11.3 动词无关性验证

阶段二测试证实：只要表达中包含「车辆报告」关键词，无论使用什么动词（查询、给我看看、我想要、生成），都能正确路由到 `generate_vehicle_report` 管线。

### 11.4 不应召回场景处理

所有不应召回的场景均能正确处理：

- 不相关查询（天气）：明确告知能力边界
- 缺少必要参数：引导用户提供信息
- 错误业务类型：明确告知功能不支持并引导正确工具
- 混淆意图：澄清需求并提供正确路径

## 13. 改进建议

### 13.1 扩展触发词列表

建议在路由规则中扩展关键词匹配，将以下近义词和语义表达纳入车辆报告生成管线的触发词：

```text
触发词建议扩展列表：
一级扩展（近义词）：
- 车况报告
- 车辆状况报告
- 安全报告
- 风险报告
- 车辆分析报告
- 车况分析
- 车辆安全分析
- 车辆风险分析

二级扩展（语义关键词）：
- 安全情况 / 安全状况 / 安全状态
- 风险情况 / 风险状况 / 风险评估 / 有什么风险
- 安全隐患 / 风险隐患
- 安全画像 / 风险画像
- 综合评分 / 风险评分
- 关注重点 / 重点风险
```

### 13.2 模糊意图识别

建议增加模糊意图的澄清机制：

```text
当用户表达为「车有问题吗」「车况怎么样」等模糊表达时：
1. 先澄清：「您是需要正式的车辆安全风险分析报告，还是只需了解基本状况？」
2. 根据用户回复决定路由
```

### 13.3 分层路由策略

建议采用分层路由策略：

```text
第一层：精确关键词匹配（车辆报告、生成报告）→ 直接路由到 generate_vehicle_report
第二层：近义词匹配（车况报告、安全分析、风险分析）→ 路由到 generate_vehicle_report
第三层：语义关键词匹配（安全情况、有什么风险、安全隐患）→ 路由到 generate_vehicle_report
第四层：模糊意图（车况、有问题吗）→ 先澄清再路由
第五层：其他表达 → 路由到 vehicle_expert 或 omni
```
