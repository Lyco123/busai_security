# 驾驶员报告路由召回率 Playwright 手动测试记录

日期：2026-04-11  
测试页面：`https://busodemo.canocache.com/assistant`  
执行方式：Playwright 手动逐条发送（不推荐本仓库内自动化脚本批量跑，便于观察每轮回复与页面状态）  
测试目标：检验驾驶员报告生成管线的路由召回率——在用户意图为「要驾驶员安全/画像类报告」时，是否稳定进入 `generate_driver_report` 对应链路；在不应进入该管线时，是否表现为澄清、拒答或进入其他合理管线，而非误生成。

## 1. 测试范围与目标

本设计聚焦**边缘**与**多轮**（不包含「正常一次性给全参数且成功出报告」的重复验证）。记录时以业务可观察行为为主：用户输入、助手最终回复、若页面展示「执行 Agent / 工具名」则一并记下。

## 2. 数据约束（仅此两组）

以下字段名与业务侧约定一致，对话中可用自然语言表述同一含义（姓名、分区日期）。

```json
{
  "driverName": "关飞鸿",
  "ppartition": "20251221"
}
```

```json
{
  "driverName": "任宇邦",
  "ppartition": "20251221"
}
```

**禁止**在测试中引入第三名驾驶员、其他分区或其他业务主键，避免干扰「路由」结论。

## 3. 执行规范

| 项 | 要求 |
|---|---|
| 会话 | **单轮边缘用例（E1–E5）**：每个用例**新建会话**。**多轮用例（M1–M5）**：全程**同一会话**内按步骤发送。 |
| 等待 | 每发送一条用户消息后 **等待约 2 分钟** 再读取助手回复；若出现「生成中」类状态，可再补等约 30–60 秒确认落点。 |
| 记录 | 建议截图或复制：用户输入、助手最终回复、若页面展示「执行 Agent / 工具名」则一并记下。 |
| 范围 | **不包含**「正常一次性给全参数且成功出报告」的重复验证；本设计聚焦**边缘**与**多轮**。 |

## 4. 判定口径（召回 / 路由）

记录时建议用下列标签归纳（便于后续算召回与误路由）：

- **R+（应召回且正确）**：用户明确要**某位驾驶员**的报告，且参数可从对话中落到「关飞鸿」或「任宇邦」之一 + 分区 `20251221`（或系统等价理解），并进入驾驶员报告生成流程（或合理澄清后进入）。
- **R−（应不召回）**：用户意图**不是**单一驾驶员报告（歧义、缺参、无关问题、明显是车辆/线路/规章等），系统**不应**在信息不足时强行生成某一位驾驶员的完整报告； acceptable 行为包括：澄清问句、拒答非业务范围、或进入非驾驶员报告管线。
- **误路由**：在 R− 场景下仍直接生成关飞鸿/任宇邦报告，或把无关问题硬套进驾驶员报告工具调用。

> 说明：前端若展示 `执行Agent: router` / 具体技能名，可作为辅助证据；最终以**用户可见结果**（是否像在走驾驶员报告、是否出现明显槽位泄漏等）为准。

| 轮次 | ID | 类型 | 核心考察点 |
|:---:|:---|:---|:---|

| 3 | E3 | 边缘·应不召回 | **两名驾驶员同时出现**，应澄清而非盲选 |
| 4 | E4 | 边缘·应不召回 | **仅分区无姓名**，应补问而非默认某人 |
| 5 | E5 | 边缘·应不召回 | **明确要车辆/车牌类报告**（无驾驶员名），不应当作驾驶员报告 |

## 6. 边缘用例（E1–E5）

### E1 — 应召回（R+）

- **新建会话**
- **用户输入（示例，可微调用语，勿改姓名与分区）：**

```text
请生成驾驶员关飞鸿的安全分析报告，数据分区日期用 20251221。
```

- **预期**：识别为驾驶员报告需求，并针对「关飞鸿」与分区 `20251221` 进入驾驶员报告生成管线（或先极短确认再进入，但不应跑成车辆/线路报告）。

### E2 — 应召回（R+）

- **新建会话**
- **用户输入：**

```text
帮我出一份任宇邦师傅上个月那份分区里的驾驶员画像报告，分区编号是 20251221，就要这个人的。
```

- **预期**：目标驾驶员唯一（任宇邦），分区明确，应稳定路由至驾驶员报告；不因「师傅」「画像」等口语而丢失 `driver_name`。

### E3 — 应不召回（R−，歧义）

- **新建会话**
- **用户输入：**

```text
关飞鸿和任宇邦两个人在 20251221 分区谁风险更高？给我各自出一份驾驶员安全报告对比一下。
```

- **预期**：两名真实驾驶员均在允许列表中，**不得**在未让用户确认的情况下直接生成其中一人报告或「合并成一份」；应澄清对比维度、是否分两次生成、或请用户先选一人。**若直接生成单人报告且无澄清 → 记为误路由高风险。**

### E4 — 应不召回（R−，缺参）

- **新建会话**
- **用户输入：**

```text
20251221 这个分区帮我拉一下驾驶员安全报告。
```

- **预期**：缺少驾驶员姓名，应追问「哪位驾驶员」，**不得**默认关飞鸿或任宇邦。

### E5 — 应不召回（R−，意图类型错误）

- **新建会话**
- **用户输入（故意不提任何驾驶员姓名；本约束下也不要编造车牌，只表达「要车辆不要驾驶员」）：**

```text
我要的是车辆安全报告，不是驾驶员个人报告。分区日期 20251221。暂时先不补充车牌，你看系统能怎么处理。
```

- **预期**：系统应走向车辆类能力或提示补充车辆信息，**不应**在无驾驶员名的前提下擅自生成关飞鸿或任宇邦的驾驶员报告。

## 7. 多轮对话用例（M1–M5）

每例：**同一会话**内按顺序发送；**每一步发送后等待约 2 分钟**。

### M1 — 需求变更

| 步骤 | 用户输入 |
|:---:|:---|
| 1 | `今天天气怎么样？` |
| 2 | `算了，业务内的事：请给我生成驾驶员任宇邦在分区 20251221 的驾驶员安全报告。` |

- **预期**：第 1 步可拒答或简短说明业务范围；第 2 步应**切换**到驾驶员报告意图，不因第 1 步而污染路由。

### M2 — 信息分散（先名后分区）

| 步骤 | 用户输入 |
|:---:|:---|
| 1 | `我要查关飞鸿的驾驶员报告。` |
| 2 | `分区日期是 20251221，刚才忘说了。` |

- **预期**：第 2 步应视为**补参**，最终仍应对「关飞鸿 + 20251221」生成或进入生成流程；中间不应出现「查无此人」类因顺序导致的断链（若出现需记录）。

### M3 — 信息分散（先分区后名）

| 步骤 | 用户输入 |
|:---:|:---|
| 1 | `先看下 20251221 分区有哪些分析能做。` |
| 2 | `那就给任宇邦出这个分区下的驾驶员安全报告。` |

- **预期**：第 2 步锁定「任宇邦 + 20251221」，路由至驾驶员报告；第 1 步若为泛化列举，第 2 步应能承接姓名。

### M4 — 追加解释（首轮模糊）

| 步骤 | 用户输入 |
|:---:|:---|
| 1 | `帮我做个安全方面的分析。` |
| 2 | `是驾驶员个人的那种综合报告，驾驶员叫关飞鸿，数据用 20251221 分区。` |

- **预期**：第 2 步应消除歧义并进入驾驶员报告管线；第 1 步允许追问，但若第 2 步已给全信息则不应再无谓拖延。

### M5 — 纠错（错误分区 → 正确分区）

| 步骤 | 用户输入 |
|:---:|:---|
| 1 | `生成任宇邦的驾驶员安全报告，分区 20251201。` |
| 2 | `分区写错了，应该是 20251221，请按这个分区重新生成。` |

- **预期**：第 2 步应**以纠正后的分区**为准继续驾驶员报告流程；若第 1 步因无数据失败，第 2 步应能恢复并成功路由（行为与《车辆报告》多轮纠错类似，可对比记录）。

## 9. 实测记录与结论

### 9.1 执行记录（2026-04-11）

执行页面：`https://busodemo.canocache.com/assistant`  
执行方式：Playwright 打开页面后，通过输入框逐条发送；单轮边缘用例新建会话，多轮用例在同一会话内连续发送。每条消息等待约 1.5-2 分钟，若仍显示“生成中”则继续等待至最终回复出现。  
执行环境：页面显示 `模拟模式`，登录身份 `Admin · 管理员`。

### 9.2 统计结论

- R+ 用例：7 条（E1、E2、M1-M5），正确进入驾驶员报告生成管线 7 条，召回率 `7/7 = 100%`。
- R− 用例：3 条（E3、E4、E5），误进入驾驶员报告生成管线 0 条，误触发数 `0/3`。
- 本轮没有发现把车辆报告、缺姓名请求或多驾驶员对比请求误生成单个驾驶员报告的情况。

### 9.3 需跟进问题

1. E3 的负例路由正确，但用户可见回复只有 `report_target_preference`，疑似内部决策标签泄漏。建议改成明确澄清文案，例如“请先选择要生成哪一位驾驶员的报告，或确认是否分别生成两份报告后再对比”。
2. M2 中“首轮未提供 `ppartition` 即查询到关飞鸿最新画像”不是当前版本的问题，而是既定行为：未提供分区时默认查询最新画像日期；用户后续补充 `ppartition` 后，再按指定分区进入报告生成。后续仅需在相关对外文案中继续保持这一规则说明，避免测试阅读时误判为缺陷。
