## 4. 判定口径

- **成功召回**：assistant metadata 中的 tool/agent 与预期报告生成管线一致。
- **数据缺失**：即使数据不存在，只要系统返回该实体对应的“未找到数据”提示，且 tool/agent 仍落在预期报告管线，仍视为路由正确。
- **误路由**：system 未落到预期报告生成管线，或 metadata/tool 显示被路由到其他通用/非目标报告管线。

## 7. 统计结论

**总体召回率**：`3 / 8 = 37.5%`  
仅 `ID 2 / 4 / 7` 明确落入预期专属管线；其余 5 条 metadata 表现为 `consult_omni`，不计为成功召回。

**分实体召回率**：

- 驾驶员报告：`1 / 2 = 50%`
- 车辆报告：`1 / 2 = 50%`
- 单位报告：`0 / 2 = 0%`
- 线路报告：`1 / 2 = 50%`

**误路由 / 非目标管线占比**：`5 / 8 = 62.5%`  
5 条用例未落入预期专属报告管线，统一表现为 `consult_omni`。

## 9. 结论

本次复测表明，报告路由系统在严格路由口径下未达到原 manual 记录的稳定性：

1. **总体召回率下降**：本轮仅 `3 / 8 = 37.5%` 命中预期专属报告管线，明显低于原 manual 的 `8 / 8 = 100%`。
2. **主要退化形态明确**：5 条未命中用例统一表现为 metadata.tool = `consult_omni`，说明请求被收敛到通用管线而非目标报告 agent。
3. **输出形态发生变化**：部分明确命中专属 agent 的回复直接返回结构化 JSON，不再完全符合原 manual 中自然语言总结报告的表现。
4. **单位类退化最明显**：单位画像报告与单位风险总结报告两条用例均未命中 `generate_unit_report`。

差异在于：本次文档严格以 metadata/tool 是否命中目标报告管线作为唯一判定依据，因此结论为 `3 / 8 = 37.5%`，不再引入额外的业务结果口径。
