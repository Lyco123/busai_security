## 4. 判定口径

- 成功召回：`tool` 命中预期报告 agent，例如 `generate_driver_report`、`generate_vehicle_report`、`generate_unit_report`。
- 未召回：返回 `consult_omni`、`router`、`null` 或其他非目标报告管线。
- 数据未命中但路由正确：如果落在目标报告 agent，只是报告内容提示“未找到数据”，仍算路由正确。
- 误路由：落入错误实体的报告 agent。本轮未出现明确误路由。

## 7. 问题分析

### 7.1 “画像风险报告” 表达召回明显弱于“风险总结报告”

- 驾驶员画像风险报告未命中，驾驶员风险总结报告命中。
- 车辆画像风险报告未命中，车辆风险总结报告命中。
- 单位画像风险报告未命中，单位风险总结报告也未命中。
- 线路画像风险报告未命中，线路风险总结报告也未命中。

说明当前路由对“风险总结报告”表述更敏感，但这一规律只在驾驶员、车辆上成立。

### 7.2 单位与线路报告管线仍未打通

- 单位两条消息都返回了接近正式报告的正文，但 `tool` 仍是 `consult_omni`，不算命中 `generate_unit_report`。
- 线路总结报告也返回了完整风险总结正文，但 `tool` 为 `consult_omni`。
- 线路画像报告直接返回“线路527在2025年12月21日的数据未找到”，且 `tool` 为 `null`。

这说明业务文案与真实路由落点已经分离，单看回复内容会高估召回效果。

### 7.3 成功命中的两条都直接输出结构化 JSON 报告

- `ID 2` 命中 `generate_driver_report`，返回管理视角 JSON 报告。
- `ID 4` 命中 `generate_vehicle_report`，返回管理视角 JSON 报告。

说明目标 agent 本身可用，但上游路由只覆盖了部分表达方式。

## 9. 结论

本轮结果与同日已有 manual 基本一致：只有驾驶员“风险总结报告”和车辆“风险总结报告”稳定命中目标报告 agent，其余 6 条均未成功召回，整体召回率为 `25%`。

当前最主要的问题不是“没有生成像报告的内容”，而是“生成了报告样式内容但没有进入对应报告 agent”。若后续要修路由，建议优先排查：

1. “画像风险报告”类意图词是否未映射到各实体报告管线。
2. 单位、线路类请求是否被 `consult_omni` 提前吃掉。
3. 前端或后端统计口径是否错误地把“有报告样式回复”当成“已命中报告 agent”。
