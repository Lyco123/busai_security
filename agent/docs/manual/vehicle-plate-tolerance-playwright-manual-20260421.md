# 车牌容错专题 Playwright 手动测试手册

日期：2026-04-21  
测试页面：`https://busodemo.canocache.com/assistant`  
执行方式：**Playwright 自动化批量执行**（API 直接调用），每条新建会话  
测试目标：验证车牌实体识别的**容错能力**——在不规范车牌写法（空格、缺失前缀、大小写、分隔符、口语化等）下，系统是否仍能正确识别并路由到 `generate_vehicle_report` 管线。

背景：4/21 上一轮车辆报告召回测试中，R+3「粤A 02650D」（中间有空格）导致实体识别失败（tool=null）。本次专项测试验证优化后的车牌容错效果。

---

## 1. 测试范围

- 本轮聚焦：**车牌不规范写法的容错**，所有用例均为车辆安全报告生成意图（应进入 `generate_vehicle_report`）。
- 标准、规范的车牌写法（粤A02650D / 粤A02013D）已在其他轮次验证，**本轮不测**。
- 10条用例覆盖7类容错场景：空格、缺前缀、大小写、分隔符、口语化拆分、粤E前缀（demo中无数据）、只给编号。

---

## 2. 数据约束

仅允许使用以下两组有完整demo数据的真实车牌：

```json
{ "numberplate": "粤A02650D", "ppartition": "20251221" }
```

```json
{ "numberplate": "粤A02013D", "ppartition": "20251221" }
```

注意：粤E前缀车牌在CSV中存在但在demo系统中无数据，测试时可使用任意粤E车牌测「容错识别+数据查无」场景。

---

## 3. 执行规范

| 项   | 要求                                                                                  |
| ---- | ------------------------------------------------------------------------------------- |
| 会话 | **每条消息单独新建会话**                                                              |
| 等待 | 每条消息等待约 2 分钟                                                                 |
| 判定 | 以 metadata `tool` 是否命中 `generate_vehicle_report` 为准                            |
| 容错 | 即使数据查无（如粤E车牌），只要路由进入了 `generate_vehicle_report`，仍算路由容错成功 |

---

## 4. 判定口径

- **路由容错成功**：不管车牌写法如何不规范，只要 `tool = generate_vehicle_report` 即算成功（数据是否查到不影响路由判定）。
- **路由容错失败**：`tool = null / consult_omni / 其他非车辆报告管线`，说明车牌容错识别未生效。

**用户输入：** 生成车辆安全报告，车牌粤A 02650D（中间有空格），日期 20251221。

## 8. 小结

- 路由容错成功数 /10：**3**（T6、T7、T8）
- 数据命中数（粤A车牌）/6：**2**（T6命中粤A02013D、T7命中粤A02013D；T1/T2/T4/T5均查无）
- 主要失败模式：
  1. **空格容错未生效**（T1/T2）：LLM将带空格的车牌原样传给工具，未做预处理。但T7（多处空格）反而成功——说明容错取决于LLM在路由决策阶段是否主动修正，而非底层工具的规范化逻辑。
  2. **大小写容错未生效**（T4）：LLM未将小写转大写，直接按原始查询。
  3. **分隔符容错未生效**（T5）：LLM未去除横杠，直接按原始查询。
  4. **自编号映射未生效**（T9）：系统不支持自编号→车牌的映射查询。
  5. **不完整车牌未补全**（T10）：LLM未自动补全缺失的「粤」和「D」。
  6. **T3服务端异常**（524 timeout）：需重新测试，暂不判定为容错问题。
- **关键发现**：T7与T1/T2同为空格场景但结果相反，差异在于LLM是否在tool参数生成阶段主动做了字符串修正。建议后续优化重点放在LLM tool参数预处理逻辑而非仅依赖底层正则。
