# Rule-Driven Agent（规则驱动智能体）概要

> 目标：让客户用“人话”配置回复规则；系统在运行时根据 Router 的命中结果，自动按规则生成稳定且自然的回复。  
> 核心原则：**Strong Router + Skills 物理隔离 + Runtime 注入 + Worker 单一职责**。  
> 关键升级：**配置能力也遵循“双轨”——对话追问（流式）与结构化编译（JSON）分离。**

---

## 1. 系统为什么要做这套东西

### 客户侧诉求
- 想控制“怎么回复”（话术、结构、禁区、必问信息）
- 不想培训成本高（不需要理解 constraints/style/template 等概念）
- 规则随业务变化频繁，最好能自助配置

### 我们侧诉求
- 规则执行稳定：少幻觉、少出错、可控
- 可扩展：规则越来越多也能维护
- 与现有架构兼容：Router 已负责匹配/命中，不在 Executor 再做匹配

## 2. 总体架构（Embedding Service + 三类技能：Ask / Build / Reply）

System runs `match_rules` in runtime before Router and injects results (no tool call from Router).

### 2.1 Embedding Service 层（规则匹配服务）

**职责**：专门负责规则的向量化与相似度匹配，不依赖 Router LLM 的判断。

**执行方式**：
- Router Pipeline: Runtime ALWAYS runs `match_rules` before Router and injects results.
- `match_rules` 工具内部使用专门的 Embedding 模型进行向量化
- 返回 topK 匹配结果（rule_id + score + metadata）

**关键特性**：
- **独立服务**：Embedding Service 作为独立工具，不依赖 Router 的 LLM 能力
- **向量化模型**：
  - **默认配置**：使用阿里云 DashScope `text-embedding-v1`（Qwen 系列）模型，默认 API 地址为 `https://dashscope.aliyuncs.com/compatible-mode/v1`
  - **可配置**：通过环境变量 `OPENAI_BASE_URL` 和 `OPENAI_EMBEDDING_MODEL` 可切换为其他兼容 OpenAI API 格式的服务（如 OpenAI、其他云服务商等）
- **匹配算法**：余弦相似度计算，返回 topK（默认 top5）候选规则
- **规则向量化**：规则保存时自动生成 embedding，存储在 `rule_json.embedding` 字段

**工具定义**：详见[附录 A.1](#a1-match_rules-工具定义)

**返回格式**：详见[附录 A.2](#a2-match_rules-返回格式)

### 2.2 Router 决策层（规则优先 + 常规路由）

**职责**：基于预计算的规则匹配结果、router skill 与工具描述进行路由决策；工作场景表只负责业务门控。

**决策流程（命中即停）**：
1. Runtime 在 Router LLM 执行前运行 `match_rules`，将 topK 结果以 `[RULE_MATCH_RESULTS]` 注入 Router 上下文（Router 本身不调用该工具）。
2. **第一优先级 — 规则匹配**：
   - 如果 top1 score ≥ threshold（0.7）→ 优先评估是否派单 `rule_reply`
   - 多条高分且分差 < 0.05 → Router 根据用户意图选最匹配的一条
3. **第二优先级 — 常规路由**：
   - 当规则未命中或不适合走 `rule_reply` 时，Router 根据 router skill 和各工具 description 选择最合适的工具
   - 当前问题不适合任何可用工具时，自然语言拒绝

**关键原则**：
- Router **不负责**向量化和匹配计算，只负责决策
- Router does NOT call `match_rules`; it decides using precomputed results.
- 规则匹配为**第一优先级**，高分命中时优先评估 `rule_reply`
- 工作场景表不再注入 Router prompt；场景只在 Router 运行前做门控

### 2.3 Skills 层（三类技能：Ask / Build / Reply）

系统新增三类技能（Skills），各司其职：

1) **Rule Asker（配置追问向导 / Conversational）**
- 面向客户：像"需求访谈"一样一步步追问，收集规则信息
- 输出：自然语言（Markdown，流式），最后给出"确认摘要"
- 产物：`rule_draft`（草稿结构，交给 runtime 存或在确认时一次性产出）

2) **Rule Builder（规则编译器 / Structured）**
- 面向系统：把 `rule_draft` 编译为内部可执行 `rule_json`
- 输出：**Strict JSON**（可校验、可存储、可版本化）
- 职责：补 defaults、规范化字段、生成 id、注入安全底线、生成 embedding

3) **Rule Reply（规则执行器 / Conversational）**
- 面向运行时：Router 已提供命中规则 IDs（以及分数）
- 负责：读取规则详情 →（v0 先取 top1）→ 按规则生成最终回复（Markdown 流式为主）

> 这三者严格遵循你们的双轨交付理念：  
> - **Path B**：Asker / Reply → Markdown（流式交互）  
> - **Path A**：Builder → Strict JSON（结构化产物）

## 3. 关键数据流（End-to-End）

### A. 规则配置流（客户配置规则：Ask → Build → Save）
1. 客户发起：描述“希望怎么回复”
2. Router 识别为“配置规则/新增规则/修改规则”场景 → 派单 `rule_asker`
3. `rule_asker` 逐步追问补齐信息（每轮 ≤2 个问题）
4. `rule_asker` 输出确认摘要 → 客户回复“确认”
5. Runtime 将 `rule_draft` 交给 `rule_builder`
6. `rule_builder` 输出严格 JSON（`rule_json`）
7. Runtime 调用 `rule_store.save(rule_json)` 保存 → 返回 rule_id / 成功提示（再由 `rule_asker` 以自然语言告知客户）

### B. 规则执行流（业务对话命中规则：Match → Reply）
1. 用户提问
2. **Runtime 预计算规则匹配**（Router 执行前）
   - Runtime 调用 `match_rules`：
     * 使用 Embedding 模型对用户查询进行向量化
     * 与规则库中的所有规则向量进行余弦相似度计算
     * 返回 topK 匹配结果（rule_id + score + metadata）
   - 将结果以 `[RULE_MATCH_RESULTS]` 注入 Router 上下文
   - 若 top1 score ≥ threshold，prompt 中附带"必须调用 rule_reply"的行动指令
3. **Router 两级优先级决策**（命中即停）
   - **第一优先级 — 规则匹配**：top1 score ≥ 0.7 → 优先评估 `rule_reply`
   - **第二优先级 — 常规路由**：规则未命中时，根据 router skill 和工具描述选择工具
4. **Rule Reply 执行**：Router 派单 `rule_reply`，把 `hit_rules + user_query` 传入
5. Runtime 调用 `rule_store.get(rule_id)` 拉详情（v0 只取 top1 跑通）
6. `rule_reply` 按规则执行：
   - 若缺必要信息 → 追问补齐
   - 否则 → 输出最终回复（Markdown，流式）

### 4.1 `rule_draft`（Asker 收集到的"人话草稿"）

完整数据结构示例详见[附录 B.1](#b1-rule_draft-数据结构示例)。

### 4.2 `rule_json`（Builder 编译后的可执行规则）

> 系统内部使用的严格 JSON 格式，包含 embedding 向量用于匹配。

完整数据结构示例详见[附录 B.2](#b2-rule_json-数据结构示例)。

### 4.3 规则数据结构设计（字段分类与职责）

#### 4.3.1 规则最小集合（v0 必须有的字段）

这组字段保证三件事：**能命中、能生成、能追问**。

##### A. 用于命中/检索

* **`match_text`**：触发描述（人话一段即可，最好带同义词）
  * 例："用户咨询违规行为/违章处理/违规记录/扣分情况/超速处理/急刹记录"
  * **这是 Anchor（锚点），保证召回率。**
* **`examples`**：用户真实语料示例（用户提供 0~2 条，模型自动补齐至 5 条）
  * 例：["我想退钱，这单还能退吗？", "订单付了款，怎么申请退款？", "这个买错了，能不能帮我退一下？"]
  * **这是 Examples（示例），提升精确率和排序质量。建议包含口语、情绪化表达。**

##### B. 用于回复生成

* **`reply_goal`**：这条规则的目标（安抚/解释政策/引导提交信息/拒绝/升级工单…）
* **`key_points`**：回复必须包含的要点（3~7 条，bullet 就行）
* **`template`（可选但 v0 强烈建议）**：一段可填空的模板（让输出稳定）
  * 示例模板格式详见[附录 B.2](#b2-rule_json-数据结构示例)中的 `template` 字段

##### C. 用于缺参追问

* **`required_info`**：缺啥就问啥（最多 1~5 个）
  * 每项包含：
    * `key`：内部键名（driver_name / violation_time / violation_type / vehicle_id）
    * `ask`：问用户的话（人话）
    * `required`：是否必填

#### 4.3.2 稳定性与安全（v0 建议字段）

这组字段控制"自由度不过头"。

* **`do_not_say`**：禁区短句列表（不保证、不泄露内部、不下法律结论…）
* **`safe_defaults`**：默认可用的事实性句子/时效/政策短句（避免编造）
  * 如 `sla="3个工作日内完成处理并通知相关人员"`、`policy_short="该违规行为已记录在案，将按制度进行处理"`
* **`tone`**：语气枚举（别让客户写"style"，就给选项）
  * `professional` / `warm` / `brief`

#### 4.3.3 多规则时代需要的字段（v1 扩展）

你现在先不做合并也没问题，但 schema 预留一下以后不痛。

* **`priority`**：优先级（0~100）
* **`scope`**：适用范围（产品线/渠道/租户/语言）
* **`enabled`**：开关
* **`version` / `updated_at`**：版本管理
* **`snippets` / `sections`**：把模板拆段，未来好合并
  * e.g. `opening`, `policy`, `ask_info`, `next_step`
* **`conflicts_with`（可选）**：显式冲突规则 ID 列表（高级用）
* **`handoff`（可选）**：触发升级/转人工/开工单的条件描述

### 4.4 客户"人话"到字段的映射

由 `rule_asker` 问出来的通常是：

* "什么时候触发？" → `match_text`
* "你希望怎么回？" → `reply_goal` + `key_points`
* "缺什么要问？" → `required_info`
* "有什么绝对别说？" → `do_not_say`
* "语气要怎样？" → `tone`
* "有没有固定话术/时效？" → `template` + `safe_defaults`

客户不需要知道字段名，Asker 只负责提问、总结；Builder 负责把答案编译成上面的结构。

## 5. Embedding Service 实现细节

### 5.1 规则向量化策略

**向量化内容**：规则的关键信息组合
- **主要使用 `match_text`**（触发描述，包含同义词，最贴近用户真实说法）
- 可选补充：`name`（规则名称）、`key_points`（要点摘要，拼接为文本）

> **注意**：`match_text` 是向量化的核心内容，应包含用户可能使用的各种表达方式（同义词、相关说法），以提高匹配准确率。

**向量化时机**：
- **新建规则**：`rule_builder` 编译时自动生成 embedding
- **更新规则**：规则修改后重新生成 embedding
- **批量更新**：支持批量重新生成所有规则的 embedding（用于模型切换）

### 5.2 匹配算法

**相似度计算**：使用余弦相似度算法，具体实现代码详见[附录 C.1](#c1-相似度计算算法)。

**混合检索策略 (Hybrid Search Strategy)**：
为了提升匹配的**精确率 (Precision)** 和 **排序质量 (Ranking)**，系统采用 **Anchor + Examples** 的混合检索策略。

- **Anchor (锚点)**：即 `match_text`，作为规则的主题标签，保证**召回率 (Recall)**。
- **Examples (示例)**：即 `examples`，包含最多 5 条用户真实语料（口语、模糊表达、情绪化表达），用户提供 0~2 条，模型自动补齐至 5 条，提升**精确率**。

**融合算法 (Max Fusion)**：
对每条规则计算最终得分：
```python
score = max(
    similarity(query, match_text),       # Anchor Score
    max(similarity(query, ex) for ex in examples)  # Max Example Score
)
```
此策略能有效解决“规则语义相近”和“用户表达口语化”导致的匹配问题。

**TopK 检索流程**：
1. 计算用户查询向量与所有规则向量（Anchor & Examples）的相似度
2.按上述 Max Fusion 策略聚合得分
3. 按相似度降序排序
4. 过滤低于 `min_score` 阈值的结果
5. 返回前 K 个结果（默认 top5）

### 5.3 工具实现（`match_rules`）

**当前实现（TypeScript/Cloudflare Workers）**：具体实现代码详见[附录 C.2](#c2-match_rules-工具实现)。

**生产环境计划（Python）**：
- 使用向量数据库（如 Milvus、Qdrant）存储规则向量，支持高效检索
- 支持批量更新和增量更新
- 支持多模型切换（通过配置切换不同的 Embedding 模型）

### 5.4 Router 集成

**Router Skill 更新**：
Router prompt must explain that rule matches are precomputed and provided as `[RULE_MATCH_RESULTS]` (see Appendix C.3).

**Router 决策逻辑**：
- Router does NOT call `match_rules`; it decides using precomputed results.
- Based on precomputed match scores:
  - 高分匹配（> 0.7）→ 调用 `rule_reply`
  - 低分或无匹配 → 调用 `consult_omni` 或其他 Worker
  - 完全不匹配 → 拒绝请求

### 5.5 冲突检测机制 (Conflict Detection)

为了防止规则重复或语义冲突，在 `rule_builder` 保存规则前，需执行**自检索 (Self-Retrieval)** 检查。

**执行逻辑**：
1. **向量化**：对当前草稿的 `match_text` 生成 Embedding 向量。
2. **自检索**：使用该向量在规则库中执行 Top-K 检索（排除当前规则 ID）。
3. **阈值判定**：
   - **红区 (> 0.92)**：**高度冲突**。视为重复规则，**阻断保存**。
     - 提示：“检测到与规则【{rule_name}】完全重复，请直接修改旧规则。”
   - **黄区 (0.80 - 0.92)**：**潜在冲突**。语义相近。
     - 提示：“检测到与规则【{rule_name}】语义相似，建议合并。是否强制保存？”
   - **绿区 (< 0.80)**：**安全**。直接保存。

### 5.6 检索质量优化：Anchor + Examples 混合策略

**为什么需要 Examples？**
模拟问题（examples/utterances）通常能明显提升“准确率/精确率”，尤其是在两类情况下：
* **用户表达很口语/隐含意图**（不是关键词直说）
* **规则彼此很像**（退款 vs 取消订阅 vs 取消预约；投诉 vs 反馈 vs 建议）

原因很直观：`match_text` 更像“主题标签”，examples 更像“真实语料分布”。embedding 检索对“真实说法”天然更友好。

#### 1) Examples 提升的是哪种准确率？

* **召回 Recall**：`match_text` 通常就不错（同义词堆一堆就行）
* **精确 Precision**：`examples` 往往提升明显（减少误命中）
* **排序质量 NDCG/MRR**：`examples` 往往提升（正确规则更容易排到 top1）

#### 2) 混合检索策略 (Hybrid Search Strategy)

我们推荐使用 **Max Fusion** 策略（简单、鲁棒）：

对每条 rule：
* `s_anchor = sim(q, anchor)`（anchor=match_text）
* `s_ex = max_j sim(q, ex_j)`（examples 取最大）
* **`score = max(s_anchor, s_ex)`**

**特点**：
* ✅ 不会因为 examples 少而漏召回（anchor 兜底）
* ✅ examples 一旦贴近真实问法，会把正确规则顶上来

#### 3) 落地建议 (v0)

* **`match_text`**: 必填（Asker 一定要拿到），作为 Anchor 保证召回。
* **`examples`**: 可选（用户给 0~2 条；模型自动补到 5 条），提升精确率。
* **小 Trick**：让模型生成 examples 时强制多样性（补齐至 5 条）：
  * 1 条"短口语"
  * 1 条"带情绪/抱怨"
  * 1 条"含糊表达"（最容易误命中的那种）
  * 1 条"正式/书面表达"
  * 1 条"场景化描述"（带时间/地点等上下文）

  name: 'match_rules',

    type: 'object',

### C. 实现代码示例

#### C.1 相似度计算算法

```python
def calculate_similarity(query_embedding, rule_embedding):
    """
    计算余弦相似度
    返回范围：[-1, 1]，值越大越相似
    """
    dot_product = np.dot(query_embedding, rule_embedding)
    norm_query = np.linalg.norm(query_embedding)
    norm_rule = np.linalg.norm(rule_embedding)
    return dot_product / (norm_query * norm_rule)
```

#### C.2 `match_rules` 工具实现

```typescript
async function executeMatchRules(
  env: Env,
  args: { query: string; top_k?: number; min_score?: number }
): Promise<ToolResult> {
  const { query, top_k = 5, min_score = 0.3 } = args;
  
  // 1. 对用户查询进行向量化
  const queryEmbedding = await generateEmbedding(env, query);
  
  // 2. 从数据库加载所有规则（包含 embedding）
  const rules = await db
    .prepare('SELECT id, name, match_text, embedding, data FROM agent_profiles WHERE kind = ?')
    .bind('rule')
    .all<RuleRecord>();
  
  // 3. 计算相似度并排序
  const matches = rules.results
    .map(rule => ({
      rule_id: rule.id,
      rule_name: rule.name,
      score: cosineSimilarity(queryEmbedding, parseEmbedding(rule.embedding)),
      metadata: extractMetadata(rule)
    }))
    .filter(match => match.score >= min_score)
    .sort((a, b) => b.score - a.score)
    .slice(0, top_k);
  
  return {
    success: true,
    data: {
      query,
      matches,
      total_matched: matches.length,
      top_k
    }
  };
}
```
