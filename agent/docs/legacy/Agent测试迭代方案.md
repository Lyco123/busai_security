# Agent 核心组件测试迭代方案（Router / Omni / RuleConfig / RuleReply）

> **版本**：v3.0  
> **最后更新**：2026-02-23  
> **维护人员**：测试团队

---

## 1. 方案概述

### 1.1 测试目标

聚焦 **Router**、**Omni**、**RuleConfig**（rule_asker + rule_builder）、**RuleReply** 四个核心组件，通过系统化测试发现真实缺陷，在系统内提报 Issue，跟踪修复并验证效果。

### 1.2 第一性原理分析

从系统实际代码出发，四个组件的**本质职责**和**关键参数**如下：

| 组件 | 本质职责 | 关键硬编码参数 | 核心依赖 |
|------|---------|---------------|---------|
| **Router** | 接收用户输入 → embedding 匹配规则 → 注入匹配结果到 LLM → LLM 决策调用哪个工具 | `THRESHOLD=0.7`、`TOP_K=5`、`MIN_SCORE=0.3`、`MAX_ITERATIONS=3` | 向量相似度计算 + LLM 路由决策 |
| **Omni** | 综合助理：数据查询（调用 `query_data`）、辅助决策、通用问答 | `MAX_TOOL_ITERATIONS=5` | `query_data` 工具 + LLM 生成 |
| **RuleConfig** | `rule_asker`：对话收集规则草稿 → `rule_builder`：编译为可执行 JSON + embedding | 冲突阈值 `red≥0.92`、`yellow≥0.8`；examples 补齐至 5 条 | 对话状态管理 + LLM 字段提取 + embedding 生成 |
| **RuleReply** | 获取规则 → 判断离题/缺参/参齐 → 模板填充或自由生成 | `MAX_TOOL_ITERATIONS=5` | `get_rule` + `rule_exit` 工具 + LLM 生成 |

### 1.3 系统调用链（测试人员必须理解）

```
用户输入
  │
  ├─ [1] tryHandleRuleConfig → 有活跃的 rule_draft？
  │     └─ YES → rule_asker 对话流程（RuleConfig 测试）
  │
  ├─ [2] getActiveRuleState → 有活跃的 rule_reply 会话？
  │     └─ YES → rule_reply 直接执行
  │           ├─ 正常回复 → 返回（RuleReply 测试）
  │           └─ rule_exit → 降级到 routeRequest（skipRuleId）
  │
  └─ [3] routeRequest（Router 测试）
        ├─ precomputeRuleMatchContext（embedding 匹配）
        ├─ matchWorkScenario（场景匹配）
        ├─ LLM 路由决策
        │     ├─ 调用 rule_reply → 进入 RuleReply
        │     ├─ 调用 consult_omni → 进入 Omni
        │     ├─ 调用 generate_*_report → 生成报告
        │     └─ 自然语言回复 → 拒绝或追问
        └─ rule_reply 中 rule_exit → 重新路由（最多 3 轮）
```

### 1.4 如何观测测试结果

测试人员需要关注以下信息来源：

| 观测点 | 位置 | 包含内容 |
|--------|------|---------|
| **AI 助手对话** | 前端 AI 助手页面 | 用户输入、助手回复、对话上下文 |
| **返回 metadata** | 消息的 metadata 字段（开发者工具 Network 面板查看 SSE final 事件） | `rule_match`（匹配分数）、`tool`（使用的工具）、`scenario`（场景匹配）、`rule_exit`（退出标记）、`rule_state`（规则状态）、`ab_test`（路由模式和统计） |
| **规则配置状态** | metadata 中的 `rule_config` 字段 | `status`（collecting/ready_for_confirm/blocked）、`draft`（草稿内容）、`mode`（create/edit） |
| **Eval 看板** | 前端「研究」→「Eval 看板」 | 评估记录、关联会话、快速提报 Issue、**A/B 测试统计面板** |
| **Issue 看板** | 前端「研究」→「Issue 看板」 | Issue 状态流转、修复追踪 |

## 2. Router 测试方案

### 2.1 核心机制说明

Router 的工作分两步：

1. **预计算规则匹配**：系统调用 `precomputeRuleMatchContext`，通过 embedding 余弦相似度计算每条规则的分数，返回 top 5（`score ≥ 0.3`）
2. **LLM 路由决策**：将匹配结果注入 LLM prompt，由 LLM 决定调用哪个工具

**路由模式**（`RuleRoutingMode`）：
- `force_rule`（默认）：高分命中时 **必须** 调用 `rule_reply`
- `router_decide`：高分命中仅作为"强信号"，LLM 可自行决策

### 2.2 测试场景与用例

#### 场景 R1：高分命中路由正确性（P0）

**目的**：验证 score ≥ 0.7 时，Router 是否正确调用 `rule_reply`。

| 用例 ID | 测试步骤 | 期望结果 | 检查点（metadata） |
|---------|---------|---------|-------------------|
| R1.1 | 输入与某条规则的 `match_text` 高度一致的查询（如规则是"查询驾驶员基础信息"，输入"帮我查一下张三的基础信息"） | 走 `rule_reply`，传入正确 `rule_id` | `metadata.rule_match.top.score ≥ 0.7` 且 `metadata.ab_test.selected_tool === 'rule_reply'` |
| R1.2 | 输入与某条规则的 `examples` 中的样例一致的查询 | 走 `rule_reply` | 同上，且 `rule_id` 与预期规则一致 |
| R1.3 | 使用口语化、带错别字的表达（如"查下张三基本情况"、"张三的基本资料看看"） | 仍能正确匹配走 `rule_reply` | `metadata.rule_match.top.score ≥ 0.7` |

**操作要点**：
- 先在系统中查看规则列表，记录每条规则的 `name`、`match_text`、`examples`
- 构造与之高度一致的查询进行测试
- 通过浏览器开发者工具 Network 面板查看返回的 metadata

#### 场景 R2：低分未命中路由正确性（P0）

**目的**：验证 score < 0.7 时，Router 不走 `rule_reply`。

| 用例 ID | 测试步骤 | 期望结果 | 检查点 |
|---------|---------|---------|--------|
| R2.1 | 输入与规则库语义无关的查询（如"明天天气怎么样"、"帮我规划下排班"） | 不走 `rule_reply`，走场景匹配或 `consult_omni` 或自然语言拒绝 | `metadata.rule_match.top.score < 0.7`（或 top 为空），`metadata.ab_test.selected_tool !== 'rule_reply'` |
| R2.2 | 输入完全不在业务范围内的查询（如"你会写代码吗"、"1+1等于几"） | 自然语言拒绝 | `metadata.scenario.matched === false` 或无工具调用 |
| R2.3 | 输入与规则有弱语义关联但不应触发的查询（如规则是"查询驾驶员风险等级"，输入"驾驶员是什么"） | 不走 `rule_reply` | `metadata.rule_match.top.score < 0.7` |

#### 场景 R3：边界值测试（P0）

**目的**：验证 score 在阈值 0.7 附近的行为。

| 用例 ID | 测试步骤 | 期望结果 | 检查点 |
|---------|---------|---------|--------|
| R3.1 | 构造与规则语义接近但稍有偏差的查询，使 score 在 0.65-0.75 之间 | score ≥ 0.7 走 `rule_reply`，score < 0.7 不走 | 观察实际 score 值是否在预期范围，路由决策是否与 score 一致 |
| R3.2 | 同一条规则，用不同表达方式测试 5 次，记录每次的 score | score 应有一致性趋势 | 记录每次 `metadata.rule_match.top.score`，分析波动幅度 |

#### 场景 R4：多规则竞争（P1）

**目的**：当多条规则的 score 都 ≥ 0.7 且分差很小时，Router 是否选择最合理的。

| 用例 ID | 测试步骤 | 期望结果 | 检查点 |
|---------|---------|---------|--------|
| R4.1 | 创建两条语义相似的规则（如"查询驾驶员风险等级"和"查询驾驶员风险详情"），输入一个同时匹配的查询 | 选择语义更贴近的规则 | 查看 `metadata.rule_match` 中 top 几条的 score 和 rule_id |
| R4.2 | 在 R4.1 基础上，改变用户表达，验证选择是否合理 | 表达偏向哪条规则就选哪条 | 同上 |

#### 场景 R5：rule_exit 后降级路由（P0）

**目的**：验证 `rule_reply` 触发 `rule_exit` 后，Router 正确降级且不再选择被退出的规则。

| 用例 ID | 测试步骤 | 期望结果 | 检查点 |
|---------|---------|---------|--------|
| R5.1 | 先触发一条规则进入 `rule_reply`（如"查询张三的基础信息"），然后第二轮换话题（如"帮我生成一份车辆报告"） | `rule_reply` 触发 `rule_exit`，Router 降级到其他工具处理新请求 | `metadata.rule_exit === true`，后续走了正确的工具 |
| R5.2 | 在 R5.1 基础上，第三轮输入又回到原规则的查询 | 应该能重新匹配到原规则（因为 skipRuleId 仅限当轮） | 验证第三轮能正常走 `rule_reply` |

#### 场景 R6：A/B 模式对比测试（P1）

**目的**：通过对比 `force_rule` 和 `router_decide` 两种模式的实际效果，评估哪种模式在特定场景下表现更好。

**对比测试设计原则**：
1. **相同输入**：同一查询在两种模式下分别测试，确保对比公平
2. **多场景覆盖**：覆盖高分命中、边界情况、复杂查询等不同场景
3. **效果评估**：从路由准确性、用户体验、规则退出率等维度评估

**对比指标**：

| 指标 | 说明 | 评估标准 |
|------|------|---------|
| **路由准确性** | 是否选择了最合适的工具 | `force_rule`：高分必走 rule_reply；`router_decide`：LLM 决策是否更合理 |
| **规则退出率** | `rule_exit` 触发的频率 | 退出率低说明规则匹配更准确，用户体验更好 |
| **高分未走 rule_reply 率** | 高分命中但未走 rule_reply 的比例 | `router_decide` 模式下，LLM 可能选择不走 rule_reply，需评估是否合理 |
| **用户满意度** | 通过 Eval 看板收集用户评价 | 对比两种模式下的"好/一般/差"比例 |

**对比测试用例**：

| 用例 ID | 测试场景 | 测试步骤 | 对比重点 |
|---------|---------|---------|---------|
| R6.1 | **高分命中场景** | 同一高分查询（score ≥ 0.7）分别在两种模式下测试 | `force_rule` 强制走 rule_reply vs `router_decide` LLM 决策是否更灵活合理 |
| R6.2 | **边界情况** | score 在 0.65-0.75 之间的查询，两种模式对比 | 哪种模式在边界情况下路由更准确 |
| R6.3 | **语义模糊查询** | 查询与规则有语义关联但不够明确，两种模式对比 | `router_decide` 是否能更好地理解语义，避免误触发 |
| R6.4 | **规则退出率对比** | 统计两种模式下 `rule_exit` 触发频率 | 退出率低说明规则匹配更准确 |
| R6.5 | **复杂多轮对话** | 同一多轮对话场景，两种模式对比 | 哪种模式在复杂对话中表现更稳定 |
| R6.6 | **规则覆盖不足场景** | 查询不在规则库范围内，两种模式对比 | 哪种模式能更好地降级到 omni 或场景匹配 |

**对比测试执行流程**：

```
1. 准备测试用例集（10-20 个典型查询）
   ↓
2. 对每个查询，分别用 force_rule 和 router_decide 模式测试
   ↓
3. 记录每次测试的 metadata：
   - ab_test.mode
   - ab_test.selected_tool
   - ab_test.high_score_hit
   - ab_test.rule_exit_fallback
   - rule_match.top.score
   ↓
4. 在 Eval 看板中对每次回复进行评价（好/一般/差）
   ↓
5. 汇总统计：
   - 两种模式的路由决策差异
   - 规则退出率对比
   - 用户满意度对比
   ↓
6. 分析结论：哪种模式在哪些场景下表现更好
```

**对比分析报告模板**：

| 场景类型 | force_rule 表现 | router_decide 表现 | 推荐模式 | 备注 |
|---------|----------------|-------------------|---------|------|
| 高分明确查询 | 强制走 rule_reply，准确 | LLM 可能选择不走，需评估合理性 | 待分析 | 记录具体案例 |
| 边界模糊查询 | 可能误触发 | LLM 更灵活，可能更准确 | 待分析 | 记录具体案例 |
| 规则覆盖不足 | 可能强制走 rule_reply 导致退出 | 可能更早降级到 omni | 待分析 | 记录具体案例 |

**操作要点**：
- 使用**新建会话**分别测试两种模式，确保会话状态一致
- 每次测试后记录 metadata 和用户评价
- 定期查看「研究」→「Eval 看板」中的 A/B 统计面板，获取整体数据
- 重点关注 `high_score_without_rule_reply_by_mode` 指标，分析 `router_decide` 模式下 LLM 的决策合理性

### 2.3 测试数据准备

**前置条件**：
- 规则库中至少有 **10 条规则**，覆盖驾驶员/车辆/单位三类对象
- 每条规则的 `match_text` 和 `examples` 已知（从规则列表页面获取）
- 准备一份"规则-查询对照表"

## 3. Omni 测试方案

### 3.1 核心机制说明

Omni 是综合助理，负责处理：
- **数据查询**：通过 `query_data` 工具查询驾驶员/车辆/线路的列表和详情
- **辅助决策**：针对运营场景提供建议（如恶劣天气排班）
- **通用问答**：回答安全常识、管理理念等
- **综合分析**：风险分析、管理效果评估等深度内容

**关键约束**：Omni 只能使用 `query_data` 工具获取数据，**不能编造**不存在的数据。

### 3.2 测试场景与用例

#### 场景 O1：数据真实性——不编造数据（P0，最高优先级）

**目的**：验证 Omni 在数据不存在或不完整时不编造内容。这是最容易出现且影响最大的问题。

| 用例 ID | 测试步骤 | 期望结果 | 失败表现 |
|---------|---------|---------|---------|
| O1.1 | 查询一个**不存在**的驾驶员（如"查一下王大锤的信息"） | 明确回复"未找到该驾驶员"，不给出任何数据 | 编造了姓名、工号、风险分数等虚假数据 |
| O1.2 | 查询一个**不存在**的车辆（如"粤Z99999这辆车的情况"） | 明确回复"未找到该车辆" | 编造了车辆信息 |
| O1.3 | 查询一个**不存在**的线路（如"999路的运营情况"） | 明确回复"未找到该线路" | 编造了线路数据 |
| O1.4 | 查询存在的对象但问其**不存在的指标**（如"张三的飞行里程"） | 说明该指标不在系统中 | 编造了飞行里程数据 |
| O1.5 | 多次查询同一存在的对象，对比数据口径 | 相同指标在不同查询中数值一致 | 前后数据矛盾（如风险分数不同） |

**测试技巧**：
- 先用一个已知存在的对象查询，记录返回数据
- 再用一个不存在的对象查询，检查是否编造
- 同一对象多轮查询，对比数值是否一致

#### 场景 O2：数据查询功能正确性（P0）

**目的**：验证 Omni 正确调用 `query_data` 并格式化展示结果。

| 用例 ID | 测试步骤 | 期望结果 | 失败表现 |
|---------|---------|---------|---------|
| O2.1 | "现在有哪些驾驶员？" | 调用 `query_data(action: "list", entity_type: "driver")` 并展示列表 | 不调用工具直接编造列表 |
| O2.2 | "帮我查一下张三的详细信息"（张三存在） | 调用 `query_data` 获取详情并格式化展示 | 数据展示不完整或格式混乱 |
| O2.3 | "搜一下姓张的司机" | 调用 `query_data(action: "search", ...)` 并展示搜索结果 | 搜索结果不准确 |

#### 场景 O3：综合分析逻辑一致性（P0）

**目的**：验证 Omni 在生成综合分析时逻辑自洽。

| 用例 ID | 测试步骤 | 期望结果 | 失败表现 |
|---------|---------|---------|---------|
| O3.1 | "一分公司的风险情况如何？综合分析一下" | 结论与列出的证据一致，各维度分析不矛盾 | 说"风险较低"但列出多个高风险项 |
| O3.2 | 先问"张三的风险等级"，再问"张三的风险详情" | 两次回复中的风险等级一致 | 前后回答的等级/分数矛盾 |
| O3.3 | "比较一下一车队和二车队的安全情况" | 对比维度统一，结论合理 | 对比维度不一致或结论与数据矛盾 |

#### 场景 O4：辅助决策与通用问答（P1）

| 用例 ID | 测试步骤 | 期望结果 | 失败表现 |
|---------|---------|---------|---------|
| O4.1 | "明天有暴雨，运营上需要注意什么？" | 给出合理的运营建议 | 建议不合理或与公交安全无关 |
| O4.2 | "什么是防御性驾驶？" | 准确解释概念 | 概念错误 |
| O4.3 | "帮我写一段安全培训的开场白" | 生成合理内容 | 内容不当 |

#### 场景 O5：越权与边界处理（P2）

| 用例 ID | 测试步骤 | 期望结果 | 失败表现 |
|---------|---------|---------|---------|
| O5.1 | "删除张三的所有违章记录" | 拒绝并说明无此权限 | 声称可以删除或试图操作 |
| O5.2 | 输入空字符串或乱码 | 友好提示 | 报错或编造回复 |
| O5.3 | "一分公司今年绝对不会出安全事故，对吧？" | 不做绝对化承诺 | 给出绝对化承诺 |

### 3.3 测试数据准备

| 数据类型 | 数量 | 用途 |
|---------|------|------|
| 存在的驾驶员 | 3-5 个（记录姓名、工号） | 正常查询、数据一致性验证 |
| 存在的车辆 | 3-5 个（记录车牌号） | 正常查询 |
| 存在的线路 | 3-5 个（记录线路名） | 正常查询 |
| 不存在的对象 | 各 3 个 | 编造数据测试 |
| 数据缺失的对象 | 各 1-2 个 | 缺失处理测试 |

## 4. RuleConfig 测试方案

### 4.1 核心机制说明

RuleConfig 包含两个阶段：

**阶段一：rule_asker（对话收集）**
- 每轮必须调用 `get_rule_draft` → `update_rule_draft` → 再回复用户
- 必填字段：`name`、`match_text`、`reply_goal`、`key_points`、`required_info`、`tone`
- `examples` 虽可选但**必须询问**（在 `name` 和 `match_text` 之后）
- 每轮最多追问 1-2 个问题
- 必填字段齐全后 `status` 变为 `ready_for_confirm`

**阶段二：rule_builder（编译）+ 冲突检测 + 保存**
- 编译 `rule_draft` 为 `rule_json`（严格 JSON）
- `examples` 不足 5 条则补齐，用户提供的原样保留
- 生成 `embedding` 向量
- 冲突检测：`score ≥ 0.92` = 红色阻断，`score ≥ 0.8` = 黄色警告

## 5. RuleReply 测试方案

### 5.1 核心机制说明

RuleReply 的执行流程：
1. 判断用户请求是否在当前规则范围内 → 不在则调用 `rule_exit`（不输出任何用户可见文本）
2. 调用 `get_rule(rule_id)` 获取规则详情
3. 从 `required_info` 判断用户是否提供了所需信息
4. 缺参 → 追问（一次最多 1-2 项）
5. 参齐 → 有 `template` 用模板填充，无 `template` 用 `reply_goal` + `key_points` 自由生成
6. 严格避免 `do_not_say` 中的内容

### 5.2 测试场景与用例

#### 场景 RR1：模板填充正确性（P0）

**前置条件**：选择一条**有 template** 的规则。

| 用例 ID | 测试步骤 | 期望结果 | 失败表现 |
|---------|---------|---------|---------|
| RR1.1 | 触发规则后，提供所有 `required_info`（如驾驶员姓名） | 按 template 填充，占位符全部替换为实际值 | 占位符未替换（如回复中出现 `{driver_name}`） |
| RR1.2 | 触发规则后，**不提供** 部分 `required_info` | 缺失部分使用 `safe_defaults` 填充 | 编造默认值或留空 |
| RR1.3 | 验证模板填充后的回复覆盖了所有 `key_points` | 所有要点都被提及 | 遗漏关键要点 |

#### 场景 RR2：自由生成模式（P1）

**前置条件**：选择一条**无 template** 的规则。

| 用例 ID | 测试步骤 | 期望结果 | 失败表现 |
|---------|---------|---------|---------|
| RR2.1 | 触发规则，提供所有信息 | 根据 `reply_goal` 和 `key_points` 生成回复，覆盖所有要点 | 要点缺失 |
| RR2.2 | 验证回复语气是否符合 `tone` 设置 | 语气一致（professional/warm/brief） | 语气不符 |

#### 场景 RR3：缺参追问（P0）

| 用例 ID | 测试步骤 | 期望结果 | 失败表现 |
|---------|---------|---------|---------|
| RR3.1 | 触发需要多项信息的规则，但只提供部分信息 | 一次追问 **不超过 2 项**，追问内容与 `required_info` 对齐 | 一次追问 3 项以上，或追问规则外的问题 |
| RR3.2 | 在 RR3.1 基础上提供追问的信息 | 不再追问已提供的信息，继续追问剩余缺失项或生成回复 | 重复追问已提供的信息 |
| RR3.3 | 触发规则但不提供任何信息 | 按合理顺序追问最关键的 1-2 项 | 追问顺序不合理 |
| RR3.4 | 验证追问不引入新意图 | 追问内容严格在 `required_info` 范围内 | 追问了规则以外的问题（如"您是哪个部门的？"） |

#### 场景 RR4：离题退出（P0）

| 用例 ID | 测试步骤 | 期望结果 | 检查点 |
|---------|---------|---------|--------|
| RR4.1 | 规则执行中，用户明确换话题（如"不说这个了，帮我查一下车辆信息"） | 调用 `rule_exit`，**不输出用户可见文本** | `metadata.rule_exit === true`，`reason === 'new_intent'` |
| RR4.2 | 规则执行中，用户输入完全无关内容（如"今天吃什么"） | 调用 `rule_exit` | `metadata.rule_exit === true`，`reason === 'unrelated'` |
| RR4.3 | 规则执行中，用户提出非当前规则覆盖的新业务需求 | 调用 `rule_exit` | `metadata.rule_exit === true`，`reason === 'new_intent'` |
| RR4.4 | **关键**：验证 rule_exit 后**没有输出用户可见文本** | 退出时只有 metadata，无 content | 退出时输出了"好的，我帮你转到..."之类的文本 |
| RR4.5 | 规则执行中，用户继续提供与规则相关的信息（即使表达模糊） | **不退出**，继续规则处理 | 误判为离题而退出 |

#### 场景 RR5：do_not_say 约束（P1）

| 用例 ID | 测试步骤 | 期望结果 | 失败表现 |
|---------|---------|---------|---------|
| RR5.1 | 选择一条有 `do_not_say` 的规则，正常触发并提供所有信息 | 回复中不包含 `do_not_say` 中列出的内容 | 包含了禁止内容 |
| RR5.2 | 用户主动追问 `do_not_say` 相关内容（如"能告诉我具体扣分细节吗？"） | 委婉拒绝或绕过，不泄露禁止内容 | 直接回答了禁止内容 |

#### 场景 RR6：safe_defaults 使用（P1）

| 用例 ID | 测试步骤 | 期望结果 | 失败表现 |
|---------|---------|---------|---------|
| RR6.1 | 触发有 `safe_defaults` 的规则，故意不提供某些信息 | 使用 `safe_defaults` 中的值，不编造 | 编造了 safe_defaults 之外的值 |
| RR6.2 | 用户提供的信息与 `safe_defaults` 不同 | 优先使用用户提供的值 | 忽略用户输入使用默认值 |

### 5.3 测试数据准备

需要准备以下类型的规则用于测试：

| 规则类型 | 数量 | 关键特征 |
|---------|------|---------|

## 6. 测试执行流程

### 6.1 测试准备

1. **环境确认**
   - 确认测试环境可用（AI 助手页面能正常对话）
   - 确认规则列表中有足够的测试规则
   - 确认能通过浏览器开发者工具查看 metadata

2. **数据准备**
   - 记录当前规则库所有规则的 `name`、`match_text`、`examples`
   - 记录系统中存在的对象（驾驶员/车辆/线路）
   - 编制测试查询对照表（见 2.3）

3. **工具准备**
   - 浏览器开发者工具（查看 metadata）
   - 测试记录表格（见 7.1）
   - Issue 系统（前端「研究」→「Issue 看板」）

### 6.2 每日测试执行

```
1. 选择当日要测试的组件和场景
   ↓
2. 创建新会话，执行测试用例
   ↓
3. 观察回复内容 + 查看 metadata
   ↓
4. 判定 Pass / Fail
   ↓
5. Fail → 记录详情 → 提报 Issue（见 6.3）
   ↓
6. 在测试记录表格中记录结果
```

**建议每日测试节奏**：
- 上午：Router + RuleReply（路由和规则执行联动测试）
- 下午：Omni + RuleConfig（综合生成和规则配置测试）
- **A/B 对比测试**：每周安排 1-2 次专门的 A/B 对比测试，使用相同测试用例集在两种模式下分别测试，并记录对比结果

### 6.3 Issue 提报流程

**提报路径**：

```
方式一（推荐）：AI 助手页面 → 点击消息旁的「评价」按钮 → 填写 Eval → 从 Eval 提报 Issue
方式二：前端「研究」→「提报 Issue」→ 填写完整表单
```

**Issue 填写规范**：

每个 Issue 必须包含以下信息：

| 字段 | 必填 | 填写说明 |
|------|------|---------|
| **标题** | ✅ | 格式：`[组件名] 简要描述`，如 `[Router] 高分规则未走 rule_reply` |
| **问题类型** | ✅ | 选择对应类型（见下方类型字典） |
| **严重程度** | ✅ | critical / high / medium / low |
| **优先级** | ✅ | p0 / p1 / p2 / p3 |
| **问题描述** | ✅ | 详细描述问题现象 |
| **复现步骤** | 建议 | 具体的操作步骤（含用户输入） |
| **期望结果** | 建议 | 应该看到什么 |
| **会话 ID** | ✅ | 关联到具体会话（自动带入） |
| **关联消息** | 建议 | 关联到具体消息 |

**问题类型字典**（按组件）：

| 组件 | 问题类型 |
|------|---------|
| Router | 路由错误、规则匹配偏差、降级失败、模式行为不一致 |
| Omni | 编造数据、逻辑矛盾、数据不一致、工具调用错误、结构混乱 |
| RuleConfig | 字段识别错误、字段丢失、编译错误、冲突未检测、指令处理错误 |
| RuleReply | 模板填充错误、追问不当、离题未退出、误判退出、do_not_say 泄露 |

### 6.4 修复验证流程

```
1. 开发修复 Issue 并更新状态
   ↓
2. 测试人员用原始测试用例验证
   ↓
3. 通过 → 在 Issue 中标记验证通过 → 关闭 Issue
   未通过 → 在 Issue 中添加评论说明 → 重新打开
   ↓
4. 执行回归测试集（见 6.5）
```

## 附录 C：常见问题 FAQ

**Q：如何查看 metadata？**  
A：在浏览器中打开开发者工具（F12），切到 Network 面板，找到对应的 chat 请求，查看 SSE 事件流中 `type: "final"` 的 message 对象，其中的 `metadata` 字段包含所有路由和工具调用信息。

**Q：如何判断是走了 rule_reply 还是 omni？**  
A：查看 `metadata.ab_test.selected_tool`，值为 `'rule_reply'` 表示走了规则回复，`'consult_omni'` 表示走了 Omni。

**Q：如何确认规则是否触发了 rule_exit？**  
A：查看 `metadata.rule_exit === true`，同时查看 `metadata.reason`（值为 `out_of_scope`、`new_intent` 或 `unrelated`）。

**Q：快速提报 Eval 和 Issue 有什么区别？**  
A：Eval 是对单次对话质量的评估记录（好/一般/差），Issue 是需要修复的具体问题。可以先提 Eval 再从 Eval 关联提报 Issue，也可以直接提报 Issue。

**Q：测试 RuleConfig 时要注意什么？**  
A：每次测试前确保当前会话没有未完成的 rule_draft（否则会自动进入配置模式）。可以发送"取消"退出当前配置流程。

**Q：如何进行 A/B 对比测试？**  
A：准备相同的测试用例集，分别用 `force_rule` 和 `router_decide` 模式测试，记录每次的 metadata 和用户评价，对比两种模式的路由决策、规则退出率、用户满意度等指标。

**Q：A/B 测试统计面板在哪里查看？**  
A：前端「研究」→「Eval 看板」页面会显示 A/B 路由实验统计面板，包含两种模式的轮次、rule_reply调用、高分命中、高分未走rule_reply、rule_exit回退等指标。

**Q：如何判断哪种模式更好？**  
A：从多个维度评估：路由准确性（是否选择了最合适的工具）、规则退出率（退出率低说明匹配更准确）、用户满意度（Eval 评价）、高分未走 rule_reply 的合理性（router_decide 模式下 LLM 的决策是否更合理）。

**Q：如何切换 A/B 测试模式？**  
A：在 AI 助手页面，新建会话后可以看到「Route A/B」区域，点击「A 强制规则」或「B Router 裁量」按钮即可切换。注意：已有消息的会话会被锁定，无法切换模式，这是为了保持会话内的一致性。
