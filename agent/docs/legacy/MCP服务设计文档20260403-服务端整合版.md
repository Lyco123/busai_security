## 2. MCP 对外协议（与当前 Agent 客户端对齐）

以下与仓库内 MCP 客户端实现一致（`agent/src/shared/mcp.ts`），服务端实现应保证行为兼容。

### 2.1 传输与端点

- 客户端向 **单一 URL**（如环境变量中的 MCP 服务根地址）发送 **HTTP POST**，负载为 **JSON-RPC 2.0**。
- 请求头（客户端会带，服务端应识别）：
  - `Content-Type: application/json`
  - `Accept: application/json, text/event-stream`
  - `MCP-Protocol-Version`：例如 `2025-03-26`（客户端默认值 `DEFAULT_MCP_PROTOCOL_VERSION`）
  - `User-Agent`：客户端可带业务标识
  - 经 **Cloudflare Access** 时可选：`CF-Access-Client-Id`、`CF-Access-Client-Secret`
  - 会话建立后，后续请求需携带响应返回的 **`MCP-Session-Id`**（客户端从响应头 `mcp-session-id` 读取）

### 2.2 会话与 RPC 方法顺序

推荐顺序（与客户端探测/调用流程一致）：

1. **`initialize`** — 协商协议版本、`clientInfo` 等；服务端通过响应头下发会话 ID。
2. **`notifications/initialized`** — 客户端就绪通知（参数可为空对象）。
3. **`tools/list`** — 返回 `result.tools[]`，每项含 `name`、`description`、`inputSchema` 等。
4. **`tools/call`** — 执行工具：`params.name` 为工具名，`params.arguments` 为 JSON 对象。

`tools/call` 的返回在 MCP 规范中多为带 `content` 的结构；客户端会对文本内容做 JSON 解析或抽取 **Original Response** 段落，网关若包装业务结果，需保证最终可被解析为与 **HTTP 层统一响应体**一致的 JSON（见第 4 节）。

### 2.3 工具发现与调用契约

- **`tools/list`**：`result.tools` 中的 **`name`** 必须与网关内部路由到下游 HTTP 时使用的逻辑名一致（见第 3 节映射）。
- **`tools/call`**：`arguments` 的键应对齐各接口的 Query / Body 字段；POST 列表类接口通常将过滤条件放在 body 对应字段，分页为 `organId`/`pageNo`/`pageSize` 等（以原文档为准）。

## 3. MCP 工具名与 HTTP 路由映射

### 3.1 命名约定（推导规则）

在现有实现中，工具名与 HTTP 路径存在稳定对应关系，便于从路径推导工具名（下划线命名）：

- 将路径 **`/mcp/{segment}/...`** 中 **`segment`** 取为 `base` 或 `ods`（第一段）。
- 后续路径片段按 **Java/Spring 风格资源名 + 方法名** 转为 **蛇形全小写段**，整体前缀为 **`get_mcp_`**。

**已在 Agent 侧代码中使用的工具名（已验证）**：

| MCP 工具名 | 下游 HTTP（方法 + 路径） | 说明 |
|------------|-------------------------|------|
| `get_mcp_base_absBusProfileMain_queryByNumberplate` | `GET /mcp/base/absBusProfileMain/queryByNumberplate` | 车辆画像（车牌 + 分区日期） |
| `get_mcp_base_odsJituanBsBus_list` | `POST /mcp/base/odsJituanBsBus/list` | 车辆明细列表 |
| `get_mcp_base_odsJituanBsBus_vehicleTypelist` | （由服务端 `tools/list` 暴露） | 车辆类型统计类能力 |
| `get_mcp_base_odsJituanBsBus_useNatureCount` | （由服务端 `tools/list` 暴露） | 使用性质统计类能力 |

### 3.2 与原文档已写 HTTP 接口的推导映射（供网关实现）

以下按第 3.1 节规则从 [`MCP服务设计文档20260403.md`](./MCP服务设计文档20260403.md) 正文中的路径推导 **建议工具名**（若线上 `tools/list` 与下表不一致，以 **`tools/list` 为真** 并回写本文档）。

| `get_mcp_base_odsJituanBsBus_list` | `POST /mcp/base/odsJituanBsBus/list` |
| `get_mcp_ods_odsJituanBsBusPark_list` | `POST /mcp/ods/odsJituanBsBusPark/list` |

## 4. HTTP 下游统一响应体（约定）

原文档前后存在多种写法，建议在 **新实现与网关** 中统一为：

- `success`：**布尔** `true` / `false`（避免字符串 `"true"`）。
- `timestamp`：数值或字符串之一，与客户端约定一致即可。
- `result`：业务数据；无数据时可为 `null` 或约定空对象，需在接口说明中写明。
- `path` / `pathArgs`：与 Agent work tools 元数据相关时填写；无则可为空对象或省略（需固定一种）。
- `message`、`code`：可选；若存在，`code` 建议与业务错误码表一致。

画像类接口中字段 **`evalutaionType`** 为历史拼写，若与数据库/API 已绑定，**服务端宜保持字段名不变**，在数据字典中标注即可。
