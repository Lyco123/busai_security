# Agent开发周报 2026-05-13

## 1. 完成无会话报告摘要接口，页面可直接生成 5 类报告

**背景**：之前报告生成主要走聊天会话。这个方式适合用户在对话里追问，但不适合页面按钮直接生成报告。页面侧如果还要先建 session、写 message，再等聊天返回，接入成本高，也不方便判断问题到底出在报告生成还是会话状态。

**方案说明**：本周新增 `POST /api/agent/reports/summary`，并支持兼容路径 `POST /api/agent/reports/summary/{type}`。接口不创建 `agent_sessions`，不写入 `agent_messages`，只根据请求字段或显式类型选择对应报告 worker。当前支持驾驶员、车辆、单位、线路、事故调查 5 类报告。前端研究页同步增加报告 API 测试页，方便直接验证请求参数、错误提示和返回结构。

**功能说明**：
- 页面按钮可以直接生成报告，不再依赖聊天会话。
- 驾驶员、车辆、单位、线路、事故调查 5 类报告都走同一个接口。
- 支持按业务字段自动识别报告类型，也支持 `id/name/nameOrId/entityId + type` 的通用调用方式。
- 缺目标、多个目标冲突、类型不支持等错误都有明确 `400` 返回。
- 增加 `report-output-format-contract` 脚本，固定 `OUTPUT_FORMAT=markdown/json` 的返回格式，避免后续改动破坏前端展示。

## 2. 完成单位/事故专家开发，所有报告对应专家管线已全部齐全

**背景**：前几周已经有车辆、驾驶员、线路专家，但单位和事故还没有独立专家。用户问单位管理效果、事故原因、事故证据或整改建议时，系统容易落到通用咨询，或者误走正式报告生成。

**方案说明**：本周新增 `unit_expert` 和 `incident_expert` 两个 conversational skill，并接入专家注册、router、工具类型、工具校验、上下文构建、结构化查询、chat-service 和 runtime。两个专家都明确只负责咨询和解释，不直接生成完整正式报告；用户明确要单位报告或事故调查报告时，仍走对应 `generate_*_report`。

**功能说明**：
- 单位专家已可承接单位基础信息、风险构成、管理效果、整改建议、下级对象风险等问题。
- 事故专家已可承接事故经过、证据解释、原因分析、责任性质、处理进度和整改建议等问题。
- 驾驶员、车辆、单位、线路、事故 5 类对象现在都有对应专家。
- 正式报告请求和专家咨询请求分得更清楚，减少“问解释却出报告”或“要报告却泛答”的情况。
- 专家回答按简单事实、单点解释、综合分析控制长度，不默认展开成长报告。

## 3. 补强 router 和 worker 约束，减少时间、字段和查询规划错误

**背景**：报告和专家变多后，router 和 worker 的误判会更明显。近期主要问题包括：用户说“今天、本周、最近”时缺少统一时间参照；结构化查询失败后提示不清楚；工具字段和业务字段容易混用；worker 在上下文不足时提前规划查询；部分 OpenAI-compatible 模型对 system message 位置更敏感。

**方案说明**：本周加入服务端时间上下文，让相对时间问题有统一参照；新增结构化 lookup 错误 responder，让未命中、解析失败、缺数据等情况能给出明确反馈；补充字段对齐、上下文检查和查询规划约束，要求 worker 先确认必要信息，再决定是否调用工具；同时修正 system message 位置，提升 Qwen 兼容性。

**功能说明**：
- “今天、本周、最近”等问题有了服务端时间基准。
- 查询失败时更容易回到澄清或说明缺什么数据，而不是含糊回答。
- worker 会更严格按工具真实字段查询，减少字段名相近导致的错查。
- 上下文不足时优先补信息，降低提前查错对象或查错条件的概率。
- Qwen 兼容场景的 message 顺序已修正。

## 4. 完成 `/chat/stream` 工具调用流式事件，咨询回答可边执行边展示

**背景**：之前 `/chat/stream` 主要返回 assistant 文本增量，工具调用过程基本不可见。用户在咨询场景里只能等最终回答，不知道系统是在生成工具参数、调用工具，还是已经拿到结果正在组织文字。

**方案说明**：本周新增 `callOpenAIWithToolsStream`，支持解析模型流式返回里的文本 delta 和 tool_calls。后端 SSE 在保留原有 `start/delta/progress/final/error/[DONE]` 的基础上，新增 `tool_call_delta`、`tool_call_ready`、`tool_execution_started`、`tool_execution_completed`、`tool_execution_failed`。前端 `sendMessageStream` 增加 `onEvent`，新助手页面会把最近几条工具活动展示在正在生成的 assistant 消息下方。

**功能说明**：
- 咨询类回答可以继续按文本 delta 实时展示。
- 前端可以看到工具准备、执行、完成、失败等状态。
- 旧前端仍可只处理 `delta/final/error`，新增事件不影响兼容性。
- 工具活动只展示最近几条，避免打断主回答阅读。
- 本轮只改 `consult_*` 类 conversational 流程；报告生成、规则配置 V2、非流式 `/chat` 和 `/reports/summary` 仍保持原有同步或结构化返回方式。

## 5. 增加流式诊断和直通探针，定位首 token 慢和输出颗粒大的原因

**背景**：流式接入后，还需要判断“第一个可见 token 晚”“输出一块一块出来”到底是哪一层造成的。可能是上游模型本来就慢，也可能是后端 SSE parser 拆事件慢，还可能是后端已经有 delta 但前端展示不够及时。

**方案说明**：本周增加 `OPENAI_STREAM_DIAGNOSTICS` 开关，默认关闭，只在排查时输出 `upstream-chunk`、`upstream-event`、`text-delta` 三类日志。随后新增 `POST /api/agent/chat/direct-stream-probe`，绕过 session、router、工具调用和 agent 聚合，直接把供应商原始 SSE 转发到浏览器。前端新增 `/research/stream-probe` 页面，记录首字节、首 event、首正文 delta、chunk 数、事件数、delta 样本和间隔样本。

**功能说明**：
- 如果首字节本身就晚，可以判断主要慢在上游模型或网络。
- 如果首 event 很早但首正文晚，说明供应商早期事件没有可见文本。
- 如果直通探针里的 text delta 本来就少且大，就不应把输出颗粒问题归因到 agent。
- 同一个 prompt 可以分别跑直通探针和正常 `/chat/stream`，对比上游基线和完整 agent 流程的差异。
- 文档里已写清诊断开关的启用、判读和后续拆除方式。
