# Agent开发周报 2026-04-08

## 1. 结构化报告数据源继续统一到 MCP：从车辆扩到驾驶员/线路，并统一最新分区策略

**背景**：上周车辆报告已经开始切到 MCP 画像数据源，但当时主要集中在车辆这一类报告，驾驶员、线路和报告 prompt 里的数据源说明还没有完全统一。本周这条线继续推进，目标是不再让不同报告类型各自维护一套取数方式、分区策略和缺数处理逻辑。

**方案说明**：本周把结构化报告数据源配置继续抽象成统一入口，分别把驾驶员报告、线路报告切到 MCP 画像工具，同时让车辆画像查询也经由统一 provider/gateway 出口处理。这样一来，报告 worker、structured lookup 和数据源说明就能围绕同一套配置收敛，而不是散落在多处临时判断。

**功能说明**：
- 将驾驶员报告切到 MCP 画像数据源，补上 driver profile 的统一读取封装
- 将线路报告切到 MCP 画像数据源，补上 route profile 的统一读取封装
- 将车辆画像查询改为通过 provider/gateway 统一访问，减少 Runtime 内直接区分 provider 的分支
- 统一 structured report prompt data sources 与数据源配置，减少报告技能、worker 和路由各自维护来源说明的情况
- 主画像类报告工具默认查询最新 partition，同时保留显式指定日期分区的能力
- 对齐车辆画像 `ppartition` 参数、lookup trace metadata 和 worker prompt UTF-8 编码处理，降低联调排查成本

## 3. Router 统一判定继续推进：去掉场景提示和硬快捷分支，让澄清、追问和查询都回到统一判定

**背景**：这段时间系统里仍然存在一些 router 之外的“捷径”：有的靠 scenario prompt 预先限定场景，有的靠 shortcut 在 router 前直接改道。这种做法短期能救单点问题，但长期会让当前轮真实意图没有完整交给 router 判断，尤其容易在报告追问、车辆元数据查询和 pending clarification 恢复时产生错分流。

**方案说明**：本周继续沿“把旁路逻辑收回 router”这条线推进。先移除 scenario routing prompt，再把 forced resume、vehicle meta query 和 structured report follow-up 这些硬快捷分支退出执行路径，改为通过 pending clarification 上下文、最近报告上下文和工具描述共同约束 router 的判断。

**功能说明**：
- 删除 scenario routing prompt，减少在 router 外预先写死场景映射
- 优先透传 clarification message，让 pending further info 的恢复继续由 router 结合当前轮判断
- 移除 forced vehicle resume、vehicle meta query、structured report follow-up 三类 router intent shortcut
- 在 router prompt 中注入最近结构化报告上下文和 pending clarification 上下文，支持报告解释、重生成和换话题场景更稳定分流
- 更新 runtime/router tool descriptions，明确 `consult_omni`、`consult_vehicle_expert` 和 `generate_*_report` 的边界
- 继续收紧 scoped tool calls，减少工具越界调用和错误抢答

## 4. 多步执行体验正式接入主链路：自然开场、报告退场与消息来源透传一起落地

**背景**：此前 agent 在查数或生成报告时，多数还是“先执行，后统一输出”，导致交互体验偏生硬；同时结构化消息和普通自然语言消息的来源信息透传也不够统一，前后端都容易出现“能生成，但解释不清是怎么来的”的问题。

**方案说明**：本周没有引入复杂 planner，而是直接在现有 worker/router/chat-service 架构外层补一层轻量多步执行编排：先生成 opening，再执行工具和 worker，最后输出正文；报告类场景在尾部再追加 closing。同时把 message sources passthrough/pipeline 统一起来，让多步执行下的来源信息继续保留下去。

**功能说明**：
- 后端链路支持查数/报告任务先输出 opening，再执行工具，最后返回正文；报告类任务末尾可追加 closing
- 流式与非流式都统一支持 `leadingContent` / `trailingContent`，保持前端只展示 agent 真实输出
- Router、worker、chat-service 统一透传 opening/closing，避免不同 worker 路径行为不一致
- 前端支持解析“自然语言前缀 + JSON 报告 + 自然语言后缀”，继续复用现有报告卡片渲染
- 统一 message sources passthrough 和 pipeline，保留报告、查询与咨询响应里的来源链路信息
- 为结构化消息与自然语言混排补齐兼容处理，降低展示错位和原始工具细节泄漏的风险

## 5. Runtime 拆分继续推进：AB 实验层和 sessions 迁出，主文件进一步收敛为组合根

**背景**：`runtime.ts` 这几周一直在做“从大而全入口退回组合根”的拆分。本周虽然用户侧可见功能不如报告链路那样集中，但结构层面的推进比较关键，因为 AB 实验、sessions 和 routing context 如果继续内联留在 Runtime 里，后续无论是改路由还是加实验都很容易相互牵连。

**方案说明**：本周重点把 AB 实验适配层和 sessions 相关实现继续外提。思路还是一样：先把高频变动、职责边界明确的部分迁成独立模块，再更新 runtime 快照文档，明确哪些已经不该再回到 Runtime 里直接写。

**功能说明**：
- 抽离 AB experiment adapter、service、metadata、types，减少 chat/router 主链路直接背负实验分组逻辑
- 新增 turn context 与相关元数据处理，统一 AB 分组、variant 和 routing mode 的传递方式
- 将 sessions repository、title service、routing context 从 Runtime 中迁出，承接会话读写、标题生成和最近 assistant routing context 读取
- 更新 `runtime.md` 结构快照，明确已迁出边界和下一轮应继续拆的 OpenAI/tooling 胶水
- 继续缩小 `runtime.ts` 对 chat、reports、sessions 的内联实现占比，保持后续演进可追踪
