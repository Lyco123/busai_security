**背景**：首屏仍可能久等 router/worker；报告 API 阶段文案易与正文重复；多轮时 opening 未进上下文会导致 worker 重复开场。

## 2. Router 主链路减负与排障

**背景**：流式探针接入后，瓶颈主要在规则匹配 → 场景匹配 → router → worker 整条链路；router prompt 和工具 schema 偏长，既费 token 也难定位慢在哪。

**亮点**：probe 模式下 **command router**（模型输出简短的 DSL 风格路由指令，不走 function-calling tools）相较原 router，在现有环境下 **路由阶段平均快约 12s，耗时约降 30%**——本周收益最大的一项。

**本周**：在不换生产 router 模型/协议的前提下，复用规则匹配的 query embedding、压缩 router skill 和 tool schema，并修正 `buildRouterTools([])`（`undefined` 全量、`[]` 无工具）。新增 pipeline probe 阶段；command router 目前仅 probe 启用，输出无效或工具不在 allow-list 时回退 function-calling，生产 `/chat/stream` 仍走原路径。

**要点**：
- 少一次重复 embedding；prompt/工具描述更短，报告/咨询/专家/规则边界保留。
- probe 可看 `rule_match_*`、`router_call_*`、`command_router_*`、`worker_started`、`main_first_delta` 等。

**提交**：`2cc05db`、`93d8d49`、`00cb5d7`、`49689dc`（2026-05-17～18）

## 3. 报告生成：工具轮次用尽时的收尾

**背景**：多轮报告/长历史下，worker 易把轮次耗在继续查数，触发超限后用户拿不到基于已有结果的答复。

**本周**：达上限前，若有工具结果则强制收尾生成（禁止再调工具）；数据不足则说明缺什么。probe 增加 `max_iterations_finalize_*`；收尾失败仍保留原超限错误。
