# 报告生成本地部署承载判断（决策版）

## 1. 先看结论

- 如果目标是“开发/测试环境可跑、少量用户可用、长报告接受排队或异步返回”，**4×3090 + 35B-A3B** 可以尝试，但不应作为正式高并发在线服务主力。
- 如果目标是“正式 API 服务、长上下文、多人同时生成报告”，**4×H100** 明显更稳妥，**35B-A3B 比 27B dense 更适合服务化部署**。
- 当前测试账单反推出的短期参考线为：**prefill 12k input tok/s、decode 360 output tok/s、embedding 660 tok/s**。4×3090 最有可能卡在 **prefill 和长上下文 KV cache**；4×H100 才有比较舒服的余量。
- 原稿最大问题不是“算错很多”，而是**没有把部署问题写成部署结论**：结论过晚、并发没有数字、正文被埋点和 session 抽样占满。

## 2. 输入数据与估算口径

- 已知账单峰值（测试环境）：
  - service LLM input：**6,168 tok/s**
  - service LLM output：**180 tok/s**
  - RAG embedding：**330 tok/s**
- 原稿据此给出了 2× 安全系数的短期对账线：**12k / 360 / 660**
- 以下速度与并发均按 **text-only API 服务** 理解；3090 默认需依赖量化，H100 默认按 BF16/FP8 服务化配置；并发分为“实用并发”和“硬顶并发”。

## 3. 部署性能估算表

| 配置 | 单路输出速度 | 节点总输出吞吐 | 实用并发 | 更适合的角色 | 判断 |
|---|---:|---:|---:|---|---|
| 4×3090 + 27B dense | 80–120 tok/s | 130–200 tok/s | 4–6 | 开发验证、少量在线请求 | 可跑，但对长报告和高并发不友好 |
| 4×3090 + 35B-A3B | 150–220 tok/s | 250–380 tok/s | 8–12 | 开发/测试、受控异步报告 | 比 27B dense 更适合服务化，但仍建议限流与排队 |
| 4×H100 + 27B dense | 160–260 tok/s | 250–420 tok/s | 8–16 | 中等并发在线服务 | 能做正式服务，但不是最优性价比 |
| 4×H100 + 35B-A3B | 300–500 tok/s | 550–900 tok/s | 18–30 | 正式 API 服务、长报告、多并发 | 这组最适合做报告生成主力 |

> 说明：以上是工程估算区间，不是供应商官方 benchmark。决定结果的变量主要有：上下文长度、量化方式、vLLM/SGLang 配置、是否开启 MTP、batch 策略以及是否把 embedding/检索与生成拆服务。

## 4. 和当前测试账单的直接对照

| 指标 | 测试账单峰值 | 短期参考线（2×） | 4×3090 + 35B-A3B | 4×H100 + 35B-A3B |
|---|---:|---:|---|---|
| LLM prefill / input | 6,168 tok/s | 12,000 tok/s | 风险最大；短上下文可争取，长报告下不稳 | 更有机会覆盖，但仍需按目标上下文压测 |
| LLM decode / output | 180 tok/s | 360 tok/s | 接近可达上沿，批量长报告时容易紧张 | 通常有较舒服余量 |
| Embedding | 330 tok/s | 660 tok/s | 建议独立部署，避免和主模型抢资源 | 建议独立部署，整体更稳 |
| 报告形态适配 | 长输入、多阶段、可能批量触发 | - | 更适合异步队列 + 限流 + 上下文上限 | 可以承接更完整的同步服务 |

**最重要的判断**：原稿给出的 12k / 360 / 660 这组数字可以保留，但必须补一句“这是对账型参考线，不是完整部署结论”。真正的部署结论应直接写成：**4×3090 只能作为受控节点，4×H100 才是更稳妥的正式服务方案。**

## 5. 建议把原稿改成这样的结构

- 第一页先给一句话结论和一张部署表，不要先写大量方法论。
- 把“受控并发”“更利于高负载”这类模糊词改成数字区间，例如单路 tok/s、节点总吞吐、实用并发。
- 把 session 关键词筛选、120 个样本抽样、前端可见字符统计移到附录；这些是辅助材料，不是部署结论本身。
- 明确假设：text-only 还是多模态、上下文长度上限、量化方式、使用的 serving 引擎，否则性能数字不可读。
- 把“是否可作为正式服务”单列出来，直接回答“能不能上、适合什么角色、风险点是什么”。

## 6. 推荐的最终表述（可直接替换原稿结论页）

> 基于当前测试环境账单峰值与报告生成形态判断，4×3090 + 35B-A3B 更适合作为开发/测试或受控异步节点，不建议直接承担正式高并发在线报告生成；4×H100 + 35B-A3B 更适合作为正式 API 服务主力。当前测试账单反推的短期参考线为 prefill 12k input tok/s、decode 360 output tok/s、embedding 660 tok/s。其中 4×3090 的主要风险不在“模型是否能加载”，而在长报告场景下的 prefill、KV cache 和批量报告并发；4×H100 在这些维度上更有余量。若短期只能使用 4×3090，应将长报告改为异步队列，限制上下文长度与同时生成数量，并将 embedding 服务拆开。

## 7. 最小可执行动作

1. 先按目标模型做一次真正有决策意义的压测：固定上下文长度（例如 32K / 64K）、固定引擎（vLLM 或 SGLang）、固定 text-only 口径，直接量出单路速度、节点总吞吐、TTFT、实用并发。
2. 若继续沿用 4×3090：默认采用 35B-A3B，不建议把 27B dense 作为报告服务主力；同时对长报告采用异步队列和并发上限。
3. 若要做正式对外或多人在线服务：优先规划 4×H100，并把 embedding 与主模型拆服务。
4. 埋点和 session 调研可以继续做，但应放到部署结论之后，作为“把账算得更准”的后续工作，而不是正文主线。
