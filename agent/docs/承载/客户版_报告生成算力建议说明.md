# 报告生成场景算力建议说明（客户版）

面向客户的阶段性部署建议：为何现阶段可先用 4×RTX 3090 完成测试，但正式生产建议采用 H100 级算力

## 1. 执行摘要

本说明面向客户，回答两个核心问题：

1. 既然 **4×RTX 3090** 在实际生产条件下几乎不可用，为什么当前测试阶段仍可以先用客户现有的 4×3090 部署？
2. 未来若要把报告生成能力从“可测试”提升到“可生产”，大致需要什么级别的算力，分别能达到什么效果？

我们的结论是：

- **4×RTX 3090 可以继续用于当前测试阶段**，因为测试阶段的目标是验证部署链路、业务流程、模型适配、提示词、RAG 与工具调用是否跑通，而不是承诺正式生产 SLA。
- **4×RTX 3090 不适合作为正式生产主力算力**。在报告生成这类长上下文、多阶段、输入远大于输出的任务中，3090 的显存容量、显存带宽、KV Cache 裕量和多卡通信能力都不足以支撑稳定生产。
- **4×H100 可以作为正式生产的入门级推荐配置**。如果目标是稳定支撑在线报告生成、较长上下文和多用户并发，H100 级别才进入“可生产”的区间。
- 若未来目标继续提升到更大上下文、更低延迟、更高并发，建议进一步考虑 **8×H100 或 H200/B200 级别** 的方案。

---

## 2. 本说明的使用边界

本文是面向客户的阶段性算力建议，核心用途是解释“测试阶段能否先用现有 4×3090”、“正式生产建议采用什么级别的算力”。

因此，本文重点回答的是：

- 哪类算力适合 **测试/联调/验收**
- 哪类算力适合 **正式生产**
- 不同算力大致能达到什么服务效果

本文不是正式 benchmark 报告，也不是采购合同附件。文中的速度、并发和适用范围属于工程测算，用于做容量级别判断与方案沟通。

---

## 3. 为什么当前测试阶段可以继续使用现有 4×RTX 3090

虽然 4×3090 不适合正式生产，但在当前阶段仍然有明显价值，原因在于测试阶段的目标和生产阶段的目标并不相同。

### 3.1 测试阶段的目标不是“顶住生产流量”，而是“验证系统是否跑通”

在当前阶段，客户更关心的是：

- 部署是否成功
- 模型是否能稳定启动
- 报告生成链路是否跑通
- RAG、工具调用、模板拼装、后处理是否正确
- 结果质量是否满足验收预期
- 提示词、流程编排和业务规则是否需要调整

这些工作对算力的要求，远低于正式生产。

### 3.2 现有 4×3090 可以承担“低并发、受控条件下”的测试任务

在对上下文长度、并发数和返回方式做控制的前提下，现有 4×3090 可以用于：

- 功能联调
- 结果验收
- 业务流程验证
- 小范围 Demo
- 内部试用
- 报告模板与提示词优化
- RAG/知识库链路调试

更具体地说，测试阶段通常可以接受以下限制：

- 控制同时生成的报告任务数量
- 对超长报告采用异步队列，而不是要求全部同步返回
- 对上下文长度做上限控制
- 对模型采用量化部署
- 允许在测试阶段接受更高的等待时间

因此，**“能继续测试”** 与 **“能正式生产”** 并不矛盾。

### 3.3 从投入产出看，测试阶段继续利用现有 4×3090 是合理的

如果客户当前已经拥有 4×3090，那么在测试阶段继续使用这批硬件，能以较低新增投入完成：

- 部署环境准备
- 模型兼容性验证
- 应用链路打通
- 业务规则调优
- 测试数据与验收流程沉淀

这意味着客户可以先完成“业务可行性验证”和“交付链路验证”，再决定何时切换到正式生产级算力。

## 4. 为什么 4×RTX 3090 在实际生产条件下几乎不可用

报告生成不同于普通短问答。它通常同时具备以下特点：

- 输入长
- 上下文长
- 多阶段调用
- RAG 参与度高
- 对稳定性要求高
- 对平均耗时和 P95 耗时更敏感

在这种场景下，真正的压力往往不是“模型能不能启动”，而是：

- 长上下文下 KV Cache 能否放得下
- 多个报告同时生成时显存是否足够
- 输入 prefill 的吞吐是否足够
- 多卡通信开销是否会拖慢整体速度
- 是否能在长时间持续运行下保持稳定

对这一类任务，4×3090 的主要问题不是“完全跑不起来”，而是**只能在很多前提限制下勉强运行**：

- 需要更激进的量化
- 需要更短的上下文上限
- 需要更严格的并发控制
- 需要更依赖异步队列
- 在长报告和批量报告场景下，稳定性和时延风险都更高

因此，从客户视角看，**4×3090 的问题不是绝对性能低，而是“可用于生产的有效性能太低”**。这会直接导致：

- 线上体验不稳定
- 可承诺的 SLA 很弱
- 运维和调优成本偏高
- 为了“让 3090 勉强可用”而付出的工程代价过大

所以它不适合作为正式生产主力算力。

## 5. 4×RTX 3090 与 4×H100 的客户视角对比

| 维度 | 4×RTX 3090 | 4×H100 |
|---|---|---|
| 建议定位 | 测试、联调、验收、Demo、受控试用 | 正式生产入门配置 |
| 是否建议承接生产主流量 | 不建议 | 建议 |
| 适合的返回方式 | 以异步队列为主，同步能力有限 | 可同时支持同步和异步 |
| 长上下文能力 | 较弱，需严格限制 | 明显更强 |
| 报告生成并发能力 | 仅适合低并发、强限流 | 可支撑稳定的中等并发生产 |
| 运行稳定性 | 对配置与负载较敏感 | 更容易做稳定生产 |
| 工程改造成本 | 较高，需要较多限制和保护策略 | 较低，更容易达到可交付状态 |
| 短期投入 | 低（若客户已有设备） | 高 |
| 生产有效性价比 | 低 | 高 |

### 5.1 性价比不能只看采购成本，还要看“可用于生产的有效吞吐”

如果只看采购成本，4×3090 当然更便宜；但如果看“可用于生产的有效吞吐”和“可承诺的服务能力”，结论会反过来：

- **对测试阶段**：4×3090 的短期性价比高，因为能利用客户现有设备，快速完成验证。
- **对正式生产**：4×3090 的性价比低，因为它虽然便宜，但无法稳定承接目标场景；为了弥补能力缺口，需要付出额外工程复杂度，最终并不划算。
- **对正式生产**：4×H100 的采购成本更高，但能显著提高“有效可用能力”，因此生产阶段的综合性价比更高。

## 6. 不同算力级别大致能达到什么效果

以下效果描述面向“报告生成服务”这一业务场景，表达的是业务能力级别，而不是单卡 benchmark 数字。

| 算力级别 | 建议角色 | 大致可达到的效果 | 适合场景 |
|---|---|---|---|
| **4×RTX 3090** | 测试/过渡节点 | 可完成部署验证、功能联调、结果验收、小范围 Demo；在强限制下支持低并发报告生成；超长报告更适合走异步 | 测试、联调、验收、PoC、内部试用 |
| **4×H100** | 正式生产入门配置 | 可稳定承接在线报告生成；可支持更长上下文、更高吞吐和更好的 P95 时延；能覆盖较明确的生产 SLA 诉求 | 正式生产、对外服务、在线生成 |
| **8×H100 或 H200/B200 级** | 增强型生产配置 | 更适合更高并发、更长上下文、更严格时延目标或更大客户规模；适合把同步体验和大批量任务同时做好 | 大规模生产、多租户、高峰负载、长报告密集场景 |

### 6.1 若目标只是“先把系统跑通”

建议继续使用现有 **4×3090**，前提是明确其定位：

- 不作为最终生产算力
- 以功能验证和业务联调为主
- 对并发和上下文做严格控制
- 以异步报告生成作为主要保障方式

### 6.2 若目标是“正式上线并可承诺服务能力”

建议直接以 **4×H100** 作为起点。

这一级别的意义不是“更快一点”，而是从根本上进入“可以稳定承接生产工作负载”的区间。对于报告生成这类长上下文任务，H100 级别在以下方面更有把握：

- 更长上下文支持
- 更稳定的多任务并发
- 更好的时延表现
- 更高的可交付 SLA
- 更低的工程约束成本

### 6.3 若未来目标是“高峰期也能保持很好的体验”

则需要考虑 **8×H100** 或 **H200/B200 级别** 的增强配置，尤其是在以下情况出现时：

- 同时在线用户继续增加
- 长报告比例明显上升
- 需要同时兼顾同步体验与批量任务
- 需要更大的上下文上限
- 需要更严格的 P95/P99 时延目标

## 7. 建议客户采用的分阶段路线

### 阶段一：继续使用现有 4×RTX 3090 完成测试与交付准备

目标：

- 跑通部署
- 跑通业务链路
- 完成功能验收
- 沉淀报告模板与提示词
- 明确正式生产的真实负载特征

建议定位：

- 测试环境
- 联调环境
- 验收环境
- 受控 PoC 环境

不建议承诺：

- 正式生产 SLA
- 大范围线上并发
- 高峰期同步长报告服务

### 阶段二：采用 4×H100 作为正式生产起点

目标：

- 支撑正式上线
- 提供明确的生产 SLA
- 支撑更长上下文和更稳定的并发
- 降低工程限制和运维压力

建议定位：

- 正式生产主节点
- 在线报告生成服务节点
- 中等规模业务负载的基线方案

### 阶段三：按业务增长升级到更高等级算力

当客户业务量、上下文长度、并发要求进一步提升时，再考虑：

- 8×H100
- H200/B200 级别
- 分层架构（在线服务与批处理拆分）

这样可以避免一开始过度投入，也避免在生产阶段长期被 3090 的能力上限束缚。

---

## 8. 最终建议

从客户视角，最重要的不是“3090 能不能勉强跑起来”，而是“什么方案对当前阶段和未来阶段分别最划算”。

因此我们的建议是：

1. **当前测试阶段**：继续利用客户现有 **4×RTX 3090**，把它定位为测试、联调、验收和 PoC 设备，快速完成部署与业务验证。
2. **正式生产阶段**：不要把 4×3090 当成生产主力方案；建议至少升级到 **4×H100** 级别，作为正式生产的起点。
3. **未来扩容阶段**：如果后续目标提升到更高并发、更长上下文或更严格 SLA，再进一步考虑 **8×H100 或 H200/B200 级别** 的增强方案。

一句话概括：

> **4×3090 适合把系统“先跑通”，但不适合把服务“真正跑稳”；4×H100 才是进入正式生产区间的起点。**
