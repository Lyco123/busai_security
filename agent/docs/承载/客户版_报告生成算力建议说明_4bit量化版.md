# 报告生成场景算力建议说明（客户版 · 4bit 量化专项）

面向客户的阶段性部署建议：4bit 量化版本在 3×RTX 3090 与 4×H100 上分别能达到什么效果，与 BF16/FP8 版本有何差异

## 1. 执行摘要

本说明面向客户，回答以下核心问题：

1. 采用 **4bit 量化** 后，Qwen3.5-35B-A3B 的显存占用、推理速度、模型精度分别会有什么变化？
2. 量化版本在 **3×RTX 3090** 和 **4×H100** 上分别能达到什么服务效果？
3. 量化版本与 BF16/FP8 版本相比，是否值得作为正式生产方案？

我们的结论是：

- **3×RTX 3090 上 BF16 版本已完全不可行**：总显存 72GB，模型权重约 70GB，加载后仅剩约 2GB，KV Cache 几乎为零，连最短上下文都无法运行。**Int4 量化是 3×3090 上唯一可行的部署方式**——权重降至约 17.5GB，剩余约 54GB 可用于 KV Cache。
- **3×3090 + Int4 可用于测试，但有明显局限**：MoE 的 256 个 expert 在 TP=3 下分布不均衡（256/3 无法整除），多卡通信效率低于 TP=2 或 TP=4；MoE Int4 的反量化开销叠加 TP=3 的不均衡分布，推理速度可能比 TP=2 或 TP=4 更差。**仅适合功能验证和受控测试，不建议作为正式生产主力**。
- **3×3090 + Int4 的另一选择是 TP=2**：只用 2 张 3090（48GB 总显存）运行 Int4 版本，第 3 张卡可用于 embedding 模型或其他辅助服务。TP=2 的 expert 分布更均衡（256/2=128），通信开销更低，但总显存更少（48GB），上下文上限更低（约 16K–32K）。
- **4×H100 + BF16/FP8 是正式生产的最优选择**，Int4 在 H100 上对 MoE 是性能退化而非提升。
- **4bit 量化会带来精度损失**，对 Agent 指令遵循、工具调用准确性有潜在影响，建议在采用前做专项精度验收。

---

## 2. 本说明的使用边界

本文是面向客户的阶段性算力建议，核心用途是解释"4bit 量化版本在 3×3090 和 4×H100 上能达到什么效果"、"与 BF16/FP8 版本相比是否更适合正式生产"。

因此，本文重点回答的是：

- 3×3090 上 BF16 和 Int4 的可行性
- TP=3 vs TP=2 的部署策略选择
- 量化版本在哪类算力上**更适合测试/联调/验收**
- 量化版本在哪类算力上**适合正式生产**

本文不是正式 benchmark 报告，也不是采购合同附件。文中的速度、并发和适用范围属于工程测算，用于做容量级别判断与方案沟通。**所有精度影响判断需以实际验收为准**。

## 3. 3×RTX 3090 的显存现实：BF16 已完全不可行

### 3.1 显存分析

3×3090 总显存 72GB（3×24GB）。Qwen3.5-35B-A3B 是 MoE 架构，总参数 35B、活跃参数约 3B。不同量化精度下的显存占用估算：

| 项目                      | BF16（原版） | Int8 量化 |    Int4 量化 |
| ------------------------- | -----------: | --------: | -----------: |
| 模型权重占用              |       ~70 GB |    ~35 GB |     ~17.5 GB |
| 3×3090 总显存             |        72 GB |     72 GB |        72 GB |
| 权重后剩余显存            |    **~2 GB** |    ~37 GB | **~54.5 GB** |
| KV Cache 可用空间（估算） | **几乎为零** | ~25–30 GB |    ~40–50 GB |
| 4×H100 总显存             |       320 GB |    320 GB |       320 GB |
| 权重后剩余显存            |      ~250 GB |   ~285 GB |    ~302.5 GB |

> 说明：以上为粗估算，实际占用取决于 vLLM PagedAttention 分配策略、框架开销、激活临时缓存等。

**关键结论**：

- **BF16 在 3×3090 上完全不可行**：72GB - 70GB = 2GB，连框架运行所需的基本显存都不够，更不用说 KV Cache。模型可能直接无法加载或启动后立即 OOM。
- **Int8 在 3×3090 上勉强可行**：剩余约 37GB，但 KV Cache 约 25–30GB，上下文上限约 16K–24K，并发路数极低。不如 Int4。
- **Int4 是 3×3090 上唯一合理的部署方式**：剩余约 54.5GB，KV Cache 约 40–50GB，可支持 16K–32K 上下文，有基本的并发能力。

### 3.2 推理速度：MoE 量化的实际情况比直觉更复杂

对 dense 模型，Int4 量化通常带来速度提升。但 **MoE 模型的 Int4 量化速度表现与直觉不同**——根据 Qwen 官方 Speed Benchmark（硬件 H20 96GB、推理引擎 SGLang），同系列 MoE 模型 Qwen3-30B-A3B 的 GPTQ-Int4 版本**在多数场景下比 BF16 更慢**：

| Input Length |          BF16 | GPTQ-Int4 (Marlin) | 比较           |
| ------------ | ------------: | -----------------: | -------------- |
| 1            |  137.18 tok/s |        31.29 tok/s | Int4 约慢 4.4× |
| 6144         |  490.10 tok/s |       120.13 tok/s | Int4 约慢 4.1× |
| 30720        | 1283.94 tok/s |       404.45 tok/s | Int4 约慢 3.2× |
| 129042       | 1385.65 tok/s |       704.82 tok/s | Int4 约慢 2.0× |

> 来源：Qwen 官方 Speed Benchmark（https://qwen.readthedocs.io/en/latest/getting_started/speed_benchmark.html）

原因：MoE 的 256 个 expert 逐 token 路由叠加反量化开销，导致内核效率不如 BF16。长上下文时差距从 4.4× 缩小到 2.0×，说明 Int4 在长输入 prefill 上的相对效率更好。

Qwen3.5-35B-A3B-GPTQ-Int4 使用了新的 `moe_wna16` 量化后端，预期性能会比 Qwen3 的 GPTQ-Marlin 更好，但**目前尚无公开 benchmark 数据**。

**3×3090 的特殊问题：TP=3 对 MoE 不友好**

- 256 个 expert 无法被 3 整除（256/3 ≈ 85.3），每张卡上的 expert 数量不均衡（85/85/86 或类似分布），导致负载不均衡和通信开销增加。
- TP=2 或 TP=4 的 expert 分布更均衡（256/2=128，256/4=64），通信效率更高。
- **3×3090 + TP=3 的 Int4 推理速度可能比理论预期更慢**——除了 MoE Int4 本身的反量化开销外，还要承受 TP=3 不均衡分布的额外惩罚。

相比之下，dense 模型的 AWQ-Int4 表现截然不同：

| 模型      | BF16 (input=1) | AWQ-Int4 (input=1) | 提升  |
| --------- | -------------: | -----------------: | ----- |
| Qwen3-8B  |          81.73 |             144.11 | +1.8× |
| Qwen3-14B |          47.10 |              96.49 | +2.0× |
| Qwen3-32B |          20.72 |              47.67 | +2.3× |

> dense 模型的 Int4 提速 1.8–2.3×，与 MoE Int4 的减速形成鲜明对比。

**修正后的估算区间**：

| 配置                  |  单路输出速度 | 节点总输出吞吐 |   实用并发 | 角色                                                |
| --------------------- | ------------: | -------------: | ---------: | --------------------------------------------------- |
| 3×3090 + 35B-A3B BF16 |    **不可行** |     **不可行** | **不可行** | BF16 完全无法运行                                   |
| 3×3090 TP=3 + Int4    |  80–130 tok/s |  140–230 tok/s |        4–8 | 测试/联调（速度受 TP=3 不均衡和 MoE Int4 双重惩罚） |
| 3×3090 TP=2 + Int4    |  90–150 tok/s |  150–260 tok/s |        3–6 | 测试/短上下文（TP=2 更均衡但显存更少）              |
| 4×H100 + BF16         | 300–500 tok/s |  550–900 tok/s |      18–30 | 正式生产入门                                        |
| 4×H100 + Int4         | 200–350 tok/s |  350–600 tok/s |      12–20 | 吞吐可能不如 BF16                                   |

> Int4 速度估算基于 Qwen3-30B-A3B GPTQ-Int4 的官方 benchmark，并做了向下调整以反映 3090 更低的带宽和 TP=3 的额外开销。moe_wna16 后端可能改善性能，但缺乏公开数据验证。

### 3.3 精度：量化损失需专项验收

Int4 量化对模型精度的影响：

- **通用问答与摘要能力**：通常只带来轻微退化，影响可控。
- **Agent 指令遵循能力**：可能削弱对复杂指令、多步约束的遵循精度，尤其在长 prompt、多 tool_choice 的场景下。
- **工具调用准确性**：JSON 格式输出、function calling 的结构化准确性可能出现偶发偏差。
- **报告结构完整性**：量化可能增加"章节遗漏""格式漂移"的风险。
- **MoE 特殊性**：expert 路由决策（gate 网络）通常不做量化，路由准确性受影响较小；但 expert 内部的权重量化可能影响输出质量。

**建议**：在决定采用 Int4 量化版本前，必须完成以下专项验收：

| 验收项             | 说明                                                         | 可接受阈值建议    |
| ------------------ | ------------------------------------------------------------ | ----------------- |
| 报告生成全链路对比 | BF16 vs Int4，对比报告内容完整性、结构一致性、关键数据准确性 | 关键指标退化 < 5% |
| 工具调用成功率对比 | BF16 vs Int4，tool_call 格式正确率                           | 正确率差异 < 3%   |
| Agent 指令遵循对比 | 复杂多步骤指令下的步骤完成率                                 | 完成率差异 < 5%   |
| 长上下文稳定性对比 | 16K/32K 上下文下的输出质量和格式稳定性                       | 格式漂移率 < 5%   |

## 4. 3×RTX 3090 + Int4 的效果与局限

### 4.1 Int4 让 3×3090 从"完全不可行"变为"受限可行"

| 维度              | 3×3090 + BF16          | 3×3090 + Int4 (TP=3)     | 3×3090 + Int4 (TP=2)     |
| ----------------- | ---------------------- | ------------------------ | ------------------------ |
| 是否可行          | **完全不可行**         | 可行                     | 可行                     |
| 模型权重占用      | ~70 GB（72 GB 总显存） | ~17.5 GB（72 GB 总显存） | ~17.5 GB（48 GB 总显存） |
| KV Cache 可用空间 | 几乎为零               | ~40–50 GB                | ~25–35 GB                |
| 可支持上下文长度  | 不可用                 | 16K–32K                  | 16K–24K                  |
| 单路输出速度      | 不可用                 | 80–130 tok/s             | 90–150 tok/s             |
| Expert 分布均衡性 | —                      | **不均衡**（85/85/86）   | **均衡**（128/128）      |
| 多卡通信效率      | —                      | 较低（TP=3 额外惩罚）    | 较高（TP=2 更均衡）      |
| 第 3 张卡用途     | —                      | 被模型占用               | 可用于 embedding/RAG     |
| 实用并发路数      | 不可用                 | 4–8                      | 3–6                      |

**关键认识**：

- **TP=3 方案**：3 张卡全部用于模型推理，显存裕量最大（54.5GB），上下文上限最高（32K），但 expert 分布不均衡，通信效率较低，单路速度可能最慢。
- **TP=2 方案**：只用 2 张卡推理，第 3 张卡可用于 embedding/RAG 服务。expert 分布均衡，通信效率更高，单路速度可能更快，但总显存更少（48GB），上下文上限更低（24K）。
- **推荐策略**：如果报告生成需要较长上下文（16K+），使用 TP=3；如果上下文需求较短（≤16K）且希望 embedding/RAG 与模型共部署，使用 TP=2。

### 4.2 为什么仍然不建议作为正式生产主力？

以下瓶颈不受量化影响：

- **显存带宽上限**：3090 的 933 GB/s 带宽是固定的。
- **PCIe 通信开销**：3090 没有 NVLink，多卡通信走 PCIe 4.0（约 64 GB/s），远低于 H100 的 NVLink（约 900 GB/s）。
- **TP=3 的额外问题**：expert 分布不均衡、all-to-all 通信模式更复杂，比 TP=2 或 TP=4 效率更低。
- **无 ECC 显存**：3090 是消费级卡，长时间高负载运行的风险高于数据中心级 H100。
- **计算单元数量**：3090 有 10496 CUDA cores，H100 有 16896 + 512 第四代 Tensor cores。

**结论**：Int4 量化让 3×3090 从"完全不可行"变为"受限可行"。它解决了显存不足的核心问题，但没有解决速度、带宽、通信、计算和稳定性的问题——反而可能让单路速度比 BF16 更慢。因此，**3×3090 + Int4 适合功能验证和受控测试，不适合正式生产主力**。

## 5. 4bit 量化版本在 4×H100 上的效果与定位

### 5.1 Int4 在 H100 上很可能不如 BF16

| 维度              | 4×H100 + BF16           | 4×H100 + Int4                   |
| ----------------- | ----------------------- | ------------------------------- |
| 模型权重占用      | ~70 GB（320 GB 总显存） | ~17.5 GB（320 GB 总显存）       |
| KV Cache 可用空间 | ~200–220 GB             | ~260–280 GB                     |
| 可支持上下文长度  | 128K+                   | 200K+                           |
| 单路输出速度      | 300–500 tok/s           | 200–350 tok/s（**大概率更慢**） |
| 实用并发          | 18–30                   | 12–20（**可能下降**）           |
| 稳定性            | 生产级稳定              | 生产级稳定（精度需验收）        |

### 5.2 H100 上采用 Int4 的决策逻辑

| 目标                           | 建议                                         |
| ------------------------------ | -------------------------------------------- |
| 正式生产、稳定服务、SLA 可承诺 | **BF16/FP8 是最优选择**                      |
| 追求更高吞吐或更高并发         | **不要用 Int4**，MoE Int4 大概率比 BF16 更慢 |
| 追求更长上下文（超过 128K）    | **Int4 有唯一价值**：KV Cache 余量更大       |
| 追求极致成本效率               | **不建议**，MoE Int4 在 H100 上是性能退化    |

**核心判断**：H100 的显存和带宽在 BF16 下已足够支撑报告生成生产服务。Int4 在 H100 上对 MoE **不是优化而是退化**——速度下降、吞吐下降，唯一的价值是更长上下文。因此，**H100 上不建议采用 Int4 量化；BF16/FP8 是最优选择**。

| 维度             | 3×3090 + BF16 | 3×3090 + Int4 (TP=3) | 3×3090 + Int4 (TP=2)          | 4×H100 + BF16 | 4×H100 + Int4         |
| ---------------- | ------------- | -------------------- | ----------------------------- | ------------- | --------------------- |
| 建议定位         | **不可行**    | 测试/长上下文验证    | 测试/短上下文+embedding共部署 | 正式生产入门  | 仅 200K+ 上下文时考虑 |
| 是否建议承接生产 | **不建议**    | **不建议**           | **不建议**                    | **建议**      | 不建议                |

| 单路输出速度     | 不可用        | 80–130 tok/s         | 90–150 tok/s                  | 300–500 tok/s | 200–350 tok/s         |

| 精度风险         | 无            | 需专项验收           | 需专项验收                    | 无            | 需专项验收            |
| 短期投入         | 低            | 低                   | 低                            | 高            | 高                    |

### 6.1 性价比评估

- **3×3090 + Int4 (TP=3)**：唯一能让 3×3090 跑起来的方式，显存裕量最大，但速度受双重惩罚（MoE Int4 + TP=3 不均衡）。适合长上下文报告的功能验证。
- **3×3090 + Int4 (TP=2)**：速度可能稍快、通信更均衡，但显存更少、上下文更短。适合短上下文功能验证 + embedding/RAG 共部署。
- **4×H100 + BF16**：正式生产的最优选择，无争议。
- **生产有效性价比排序**：4×H100 BF16 > 4×H100 FP8 > 3×3090 Int4 TP=3（长上下文） > 3×3090 Int4 TP=2（短上下文） > 4×H100 Int4（大概率性能退化） > 3×3090 BF16（不可行）。

## 7. 不同量化 + 硬力级别大致能达到什么效果

| 算力 + 量化级别                    | 建议角色                      | 大致可达到的效果                                                                  | 适合场景                    |
| ---------------------------------- | ----------------------------- | --------------------------------------------------------------------------------- | --------------------------- |
| **3×RTX 3090 + BF16**              | **不可行**                    | 模型权重几乎塞满全部显存，KV Cache 几乎为零，**无法运行**                         | —                           |
| **3×RTX 3090 + Int4 (TP=3)**       | 测试/长上下文验证             | 可支持 16K–32K 上下文；速度 80–130 tok/s；精度需验收；expert 分布不均衡           | 长上下文报告联调、验收、PoC |
| **3×RTX 3090 + Int4 (TP=2)**       | 测试/短上下文+embedding共部署 | 可支持 16K–24K 上下文；速度 90–150 tok/s；第 3 张卡可跑 embedding/RAG；精度需验收 | 短上下文功能验证、RAG 调试  |
| **4×H100 + BF16**                  | 正式生产入门（首选）          | 128K+ 上下文；18–30 并发；300–500 tok/s；最好的 SLA                               | 正式生产、对外服务          |
| **4×H100 + FP8**                   | 生产增强                      | 精度近无损；吞吐可能更高                                                          | H100 追求更高吞吐           |
| **4×H100 + Int4**                  | 仅长上下文专用                | 吞吐大概率不如 BF16；唯一价值 200K+ 上下文                                        | 仅 200K+ 上下文场景         |
| **8×H100 或 H200/B200 + BF16/FP8** | 大规模生产                    | 更高并发、更长上下文、更严格 SLA                                                  | 大规模生产、多租户          |

### 7.1 若目标只是"先把系统跑通"

根据实际场景选择：

- **BF16 完全不可行**，3×3090 必须使用 Int4 量化版本。
- **长上下文验证（16K+）**：使用 3×3090 + Int4 **TP=3**，3 张卡全部用于模型推理，显存裕量最大。
- **短上下文验证 + RAG 调试（≤16K）**：使用 3×3090 + Int4 **TP=2**，第 3 张卡可跑 embedding/RAG 服务，整体更均衡。
- 前提条件：
  - 完成精度专项验收
  - 明确定位为测试/联调设备，不作为最终生产算力
  - 长报告仍建议走异步队列
  - 建议先做 TP=3 vs TP=2 的对比压测，确认哪种策略更适合目标场景

### 7.2 若目标是"正式上线并可承诺服务能力"

- **首选**：4×H100 + **BF16**。
- H100 在 BF16 下是最优选择——速度最快、精度最高、稳定性最好。
- 如需更高吞吐，推荐 H100 + **FP8**，**不建议 Int4**。

### 7.3 若目标是"在同等硬件上最大化吞吐"

- **H100 上最大化吞吐的路径是 BF16 或 FP8，而非 Int4**。
- MoE Int4 在当前推理引擎下速度大概率不如 BF16。
- **dense 模型**的 AWQ-Int4 可提升吞吐 1.3–1.5×，但 35B-A3B 是 MoE，不适用这一规律。

## 8. 建议客户采用的分阶段路线

### 阶段一：3×RTX 3090 + Int4 量化完成测试与交付准备

目标：

- 跑通部署（Int4 版本，选择 TP=3 或 TP=2）
- 跑通业务链路
- 完成 Int4 精度专项验收
- 完成功能验收
- 沉淀报告模板与提示词
- 明确正式生产的真实负载特征

> 注意：Int4 让 3×3090 从"完全不可行"变为"受限可行"，但带宽、PCIe 通信和稳定性瓶颈不受量化影响。

建议定位：

- 测试环境（Int4 版本）
- 联调环境
- 验收环境
- 受控 PoC 环境

不建议承诺：

- 正式生产 SLA
- 大范围线上并发
- 高峰期同步长报告服务

### 阶段二：4×H100 + BF16/FP8 作为正式生产起点

目标：

- 支撑正式上线
- 提供明确的生产 SLA
- BF16 精度下保证报告生成质量
- 支撑更长上下文和更稳定的并发
- 降低工程限制和运维压力

建议定位：

- 正式生产主节点（BF16）
- 在线报告生成服务节点
- 中等规模业务负载的基线方案

### 阶段三：按业务增长升级到更高等级算力

当客户业务量、上下文长度、并发要求进一步提升时，再考虑：

- 8×H100（BF16 或 FP8）
- H200/B200 级别
- 分层架构（在线服务与批处理拆分）

---

## 9. 最终建议

从客户视角，3×3090 + BF16 完全不可行，Int4 是唯一可行选项，但 3×3090 + Int4 仅适合测试，不适合正式生产。4×H100 + BF16/FP8 是正式生产的最优选择。

因此我们的建议是：

1. **当前测试阶段**：采用 **3×RTX 3090 + Int4 量化版本**（TP=3 或 TP=2），定位为测试、联调、验收和 PoC 设备。**仍需完成精度专项验收**。
2. **正式生产阶段**：采用 **4×H100 + BF16/FP8**，作为正式生产起点。
3. **未来扩容阶段**：如果后续目标提升到更高并发、更长上下文或更严格 SLA，再进一步考虑 **8×H100 或 H200/B200 级别**。

一句话概括：

> **3×3090 + BF16 完全不可行，Int4 是唯一能跑起来的方式但仅适合测试；4×H100 + BF16/FP8 才是正式生产起点。**
