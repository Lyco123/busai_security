# 报告生成用量与吞吐估算简报

## 重要说明：数据环境与结论范围

- **环境**：本文中的账单 Token 数据、管理员 session 抽样等均来自**测试/开发环境**（非生产），反映的是该环境下一段时间内的使用形态，**不能**当作生产用量、生产峰值或生产业务形态的外推依据。
- **作用范围**：在有生产或准生产监控数据之前，这些数字的用途很有限，主要用于：① 在**同一测试系统**上理解账单能告诉我们什么；② 为后续埋点、压测方法提供**方法框架**；③ 对本地部署自测给出**与当前测试账单峰值挂钩**的粗验收参考（见下文「测试账单峰值」表述）。
- **需求与现状部分**：第 3 节（埋点建议）、第 8 节（session 调研）等以**产品/业务调研、口径说明与改进建议**为主，并非通过完整、权威的系统级统计或生产监控得出；其中关键词筛选、人工抽样、前端可见字符等，都属于**调研手段**，与「系统精确计算出的」结论需区分看待。
- **可确定的结论类型**：在本文前提下，**能负责任给出的**主要是：从**现有测试系统账单**能聚合出的峰值/总量、以及**方法论上**若补齐任务级数据后应如何推算吞吐；任何涉及「生产上需要多少机」「生产 SLA」的表述，在本文中均为**方法占位或目标形态讨论**，**不是**已用生产数据校验过的结论。

## 3. 报告生成用量应该怎么调研（系统能力 vs 业务调研）

现有账单只能告诉我们“某一分钟用了多少 input/output/embedding tokens”，但报告生成需要知道“每份报告用了多少 tokens、用了几次模型调用、耗时多久”。**本节是设计与口径建议**（从研发与可观测性角度出发），**不是**已落库、已跑全量的系统计算结果。若要在**未来生产或准生产**上回答用量问题，需要按以下口径（或等价口径）在系统里落实埋点与聚合。

### 3.1 在报告生成入口记录任务级 ID

每次报告生成必须生成一个稳定的 `report_task_id`，贯穿所有 LLM、RAG、工具调用。

建议字段：

| 字段 | 说明 |
|---|---|
| `report_task_id` | 单份报告唯一 ID |
| `report_type` | 车辆报告、线路报告、日报、周报、风险分析等 |
| `user_id` / `tenant_id` | 用于区分业务方 |
| `created_at` | 任务创建时间 |
| `started_at` | 开始生成时间 |
| `finished_at` | 完成时间 |
| `status` | success / failed / timeout / cancelled |
| `section_count` | 报告章节数 |
| `data_range` | 报告覆盖的数据范围 |
| `rag_enabled` | 是否走 RAG |
| `model_name` | 使用的模型 |

### 3.2 在每次模型调用记录 token 用量

每次 LLM 调用记录：

| 字段 | 说明 |
|---|---|
| `report_task_id` | 归属报告任务 |
| `call_id` | 单次模型调用 ID |
| `call_stage` | outline / retrieve / section_generate / summarize / polish / final_check |
| `input_tokens` | 输入 tokens |
| `output_tokens` | 输出 tokens |
| `cached_input_tokens` | 命中的缓存输入 tokens |
| `start_time` | 调用开始时间 |
| `end_time` | 调用结束时间 |
| `first_token_latency_ms` | 首 token 延迟 |
| `total_latency_ms` | 总耗时 |
| `error_code` | 错误码 |

每次 embedding 调用记录：

| 字段 | 说明 |
|---|---|
| `report_task_id` | 归属报告任务 |
| `embedding_call_id` | embedding 调用 ID |
| `embedding_stage` | query_embedding / document_embedding / rerank_input 等 |
| `embedding_tokens` | embedding tokens |
| `chunk_count` | chunk 数量 |
| `latency_ms` | 耗时 |

### 3.3 按报告任务聚合

有了任务级日志后，每份报告可以得到：

```text
report_input_tokens = sum(input_tokens)
report_output_tokens = sum(output_tokens)
report_cached_input_tokens = sum(cached_input_tokens)
report_embedding_tokens = sum(embedding_tokens)
report_model_calls = count(llm_calls)
report_duration_s = finished_at - started_at
```

重点统计：

| 指标 | 用途 |
|---|---|
| 平均 tokens/报告 | 估算日常容量 |
| P50 tokens/报告 | 典型报告 |
| P90 tokens/报告 | 偏重报告 |
| P95 tokens/报告 | 容量规划基准 |
| P99 tokens/报告 | 峰值保护、限流依据 |
| 平均 output tokens/报告 | decode 压力 |
| 平均 input tokens/报告 | prefill 压力 |
| 平均 embedding tokens/报告 | RAG/embedding 压力 |
| 平均耗时/报告 | 并发估算 |
| 最大并发报告数 | 服务池和排队设计 |

## 4. 如何从每份任务 token 推出吞吐

报告生成吞吐不能只看“每天几份报告”，必须看峰值窗口。例如 10 分钟内集中生成 50 份报告，压力远高于一天平均 50 份。

### 4.1 单份报告 token 模型

假设统计得到：

```text
P95 每份报告 input_tokens = I
P95 每份报告 output_tokens = O
P95 每份报告 embedding_tokens = E
P95 每份报告耗时目标 = T 秒
峰值并发报告数 = N
```

则需要的吞吐为：

```text
LLM prefill 吞吐 >= N * I / T
LLM decode 吞吐 >= N * O / T
Embedding 吞吐 >= N * E / T
```

如果是按峰值时间窗口估算：

```text
窗口内报告数 = R
窗口时长 = W 秒

LLM prefill 吞吐 >= R * I / W
LLM decode 吞吐 >= R * O / W
Embedding 吞吐 >= R * E / W
```

（方法论）容量规划在具备**可信环境的生产或准生产**历史峰值后，通常再乘安全系数：

```text
目标环境建议容量 = 该环境历史峰值吞吐 * 1.5 ~ 3
```

上式中「历史峰值」须与目标环境一致；**本文测试账单不替代生产峰值。**

### 4.2 用当前**测试环境**账单给出短期参考下限

在没有任务级日志前，可先用**本测试/开发环境**账单峰值，作为**与当前测试账单同口径的**粗参考下限（用于本地/测试部署对照），**不**应理解为生产环境容量承诺。

当前 service 侧峰值（**测试环境账单**）：

```text
input 峰值 = 6,168 tokens/s
output 峰值 = 180 tokens/s
```

按 `2x` 安全系数：

```text
目标 prefill 能力 >= 12,000 input tokens/s
目标 decode 能力 >= 360 output tokens/s
```

RAG/embedding 峰值：

```text
embedding 峰值 = 330 tokens/s
```

按 `2x` 安全系数：

```text
目标 embedding 能力 >= 660 embedding tokens/s
```

这组数字可视为：在**与本文同一测试账单来源、同一统计口径**下，本地自测/开发环境压测的**对账型**最低参考线；正式生产或对外 SLA 需另用**目标环境**数据重新标定。

## 5. 报告生成的推荐压测方式

不要只压测单轮问答，要模拟完整报告任务。

### 5.1 构造压测样本

从**有代表性的报告用例**中抽样（可来自业务回归集或**当前测试/开发**环境中的长文档，**不必定**是生产数据），至少准备：

| 样本类型 | 用途 |
|---|---|
| 小报告 | 验证轻量场景 |
| 中报告 | 日常主力场景 |
| 大报告 | P90/P95 场景 |
| 超大报告 | P99、保护策略、限流策略 |

每类报告记录：

```text
章节数
RAG 查询次数
工具调用次数
input_tokens
output_tokens
embedding_tokens
总耗时
```

### 5.2 压测阶梯

建议并发阶梯：

```text
1, 2, 4, 8, 16, 32, 64
```

每一档至少跑 10 到 30 分钟，记录：

```text
成功率
P50/P90/P95/P99 总耗时
P50/P90/P95/P99 首 token 延迟
input tokens/s
output tokens/s
embedding tokens/s
GPU 利用率
显存占用
KV cache 使用率
队列等待时间
超时率
```

### 5.3 验收线

基于**当前测试环境账单**推导的短期、自测向验收参考（**非**生产合同口径）：

```text
service prefill >= 12k input tokens/s
service decode >= 360 output tokens/s
embedding >= 660 tokens/s
报告任务成功率 >= 99%
报告生成 P95 耗时满足业务 SLA
GPU 显存峰值保留 10%~20% 余量
```

如果 `4 x 3090` 达不到这些指标，应优先做：

```text
限制单份报告最大上下文
限制同时生成报告数量
报告章节串并行策略优化
开启 prompt cache / prefix cache
embedding 服务和 LLM 服务拆开部署
对 3090 使用 INT8 或 INT4 量化
长报告走异步队列，不承诺同步返回
```

## 6. 对当前硬件的判断

`QWEN3.6 35B A3B` 在 `4 x 3090` 上可以作为**开发/测试环境**试运行或受控并发部署，但不建议在没有**目标环境**压测与数据前，把本文中的数字当作**生产峰值 SLA 承诺**。

原因（与测试账单、报告形态强相关，仍属**定性+测试数据提示**）：

- 35B 权重即使能放进 `4 x 24GB`，KV cache 和长上下文并发会很紧。
- 报告生成通常 input 很长，prefill 压力明显高于普通问答。
- 报告生成可能包含多阶段调用，单份报告会放大总 token 消耗。
- **在本文测试环境账单中**，峰值约 `6.2k input tokens/s`；若将「安全系数 2x」**仅作为同一测试口径下的对账式放大**（非生产已验证需求），对 prefill 的粗参考会落在约 `12k input tokens/s` 量级，**该数值不代表生产已验证目标**。

`4 x H100` 从硬件能力上**一般更利于**高负载下的报告类长上下文与多并发，但具体是否用于生产、如何配置，仍需以**生产或准生产**的用量与压测为准。

## 7. 最小落地方案

以下步骤是**在目标环境（含未来生产）上建立可信用量**的通用顺序；在**仅开发/测试**阶段，可缩小范围，但**不应**用测试环境的一次性数据冒充生产结论。

第一步：在目标部署链路上补充报告任务级埋点。

```text
report_task_id
report_type
LLM input/output/cached tokens
embedding tokens
模型调用次数
报告耗时
错误/超时
```

第二步：在**要服务的那个环境**（准生产/生产或代表性沙箱）连续采集 3 到 7 天报告生成数据；**仅测试环境**的短期样本不能替代上式中的「真实」生产形态。

第三步：输出每类报告的 token 分布。

```text
P50/P90/P95/P99 input tokens/报告
P50/P90/P95/P99 output tokens/报告
P50/P90/P95/P99 embedding tokens/报告
P50/P90/P95/P99 duration/报告
```

第四步：用 P95 每份报告 token 和峰值窗口报告数反推吞吐。

```text
prefill tokens/s = 峰值窗口报告数 * P95 input tokens/报告 / 窗口秒数
decode tokens/s = 峰值窗口报告数 * P95 output tokens/报告 / 窗口秒数
embedding tokens/s = 峰值窗口报告数 * P95 embedding tokens/报告 / 窗口秒数
```

第五步：用**代表性**报告样本在目标硬件（如 `4 x 3090`）上压测，看是否达到与**该次压测/账单口径一致**的参考线，例如下组数字（**来自本文测试账单的 2x 对账，非生产合同**）：

```text
prefill >= 12k input tokens/s
decode >= 360 output tokens/s
embedding >= 660 tokens/s
P95 报告耗时满足业务 SLA（SLA 须单独定义并基于目标环境验证）
```

如果达不到，应把报告生成做成异步队列、控制并发，并把 `4 x 3090` 在能力评估上定位为**受控/低并发**节点；是否引入 `4 x H100` 等由**目标环境容量与成本**决定，**不能**仅由本文测试数据推导。

### 8.5 对吞吐估算的影响

以下将第 8.4 节的**测试环境、前端可见字符**抽样与**第 2 节测试环境账单**结合，做**示意性**推算，用来说明 decode 与账单峰值之间**可能**存在张力；**不是**经服务端 token 对账的精确结论，也**不是**生产需求。

按抽样结果，报告生成的可见输出 P95 约 `12.5k` 字符。粗略按中文 `1 字符 ≈ 1 token` 估算，P95 报告的可见 output 约 `12k tokens` 量级。

如果峰值窗口内同时生成 `R` 份 P95 报告，窗口为 `W` 秒：

```text
decode tokens/s >= R * 12,500 / W
```

例如：

```text
10 分钟内生成 20 份 P95 报告：
decode >= 20 * 12,500 / 600 = 417 tokens/s
```

这已经高于账单短期建议线 `360 output tokens/s`。因此报告生成对 decode 的压力不能忽略，特别是长报告和批量报告。

input/prefill 仍不能从前端消息精确还原。建议尽快补充服务端埋点：

```text
report_task_id
task_type=report_generation
input_tokens
output_tokens
cached_input_tokens
embedding_tokens
call_stage
latency_ms
```

然后用真实任务级 token 重新计算：

```text
prefill tokens/s = 峰值窗口报告数 * P95 input tokens/报告 / 窗口秒数
decode tokens/s = 峰值窗口报告数 * P95 output tokens/报告 / 窗口秒数
embedding tokens/s = 峰值窗口报告数 * P95 embedding tokens/报告 / 窗口秒数
```
