# Omni / Router 问题汇总（2026-03-16）

## 目标

汇总 2026-03-16 对 BUSO Demo 智能助手进行的手工会话测试中，已确认的问题、复现模式、影响范围和根因判断。

测试重点包含：

- 报告生成后继续追问的多轮场景
- 信息不全时的澄清场景
- 正常单轮请求场景
- 部分“理论上应由 omni 全程处理”的业务咨询场景

## 核心结论

### 1. `router回复业务内容` 是已稳定复现的主问题

当用户先成功拿到线路/车辆/驾驶员报告，再继续追问：

- 为什么某个风险排第一
- 给我两条管理动作
- 只给我一条今天先做的动作
- 这几条里哪条适合本周先做

系统在前几轮可能还能正常走：

- `generate_route_report`
- `generate_vehicle_report`
- `consult_omni`

但一旦问题进入“建议、优先级、管理动作”这类依赖报告上下文的业务分析，`router` 会直接自己回答业务内容，而不是继续路由给 `omni/consult`。

这类问题已在以下对象上复现：

- 线路
- 车辆
- 驾驶员

### 2. 问题不只发生在长对话

更准确地说：

- `router回复业务内容` 这一类问题，当前最稳定地出现在多轮报告后追问里
- 但短对话同样存在问题，只是表现形式更多是：
  - 实体解析错误
  - 关键词误判
  - 生成过程卡住

因此不能说“只有长对话有问题”。

### 3. 第一层解释通常正常，但不是全链路稳定

在“报告已成功生成”的样本里，第一层解释通常会由 `consult_omni` 正常回答。

但全链路上并不能说“第一层解释总是正常”，原因是：

- 有些会话在进入解释前就已经因为实体解析失败而被 `router` 截断
- 有些短链路会直接卡在“正在生成...”，无法稳定进入后续解释阶段

## 已确认问题

### 问题 A：`router回复业务内容`

#### 表现

在已生成报告的上下文里，用户继续问管理动作、优先级、落地建议时，`router` 直接输出业务结论。

#### 期望行为

这类问题应继续交给 `omni/consult` 处理，`router` 只负责路由，不应直接给业务答案。

#### 已复现模式

1. 线路报告 -> 解释风险原因 -> 追问本周动作 -> `router` 直接回答
2. 车辆报告 -> 解释能耗风险原因 -> 追问今天先做什么 -> `router` 直接回答
3. 驾驶员报告场景中，后续建议类追问也出现相同倾向

#### 影响

- 破坏 agent 边界
- 让路由层承担业务推理
- 后续行为不稳定，难以保证回答质量和一致性

#### 根因判断

- `router` 缺少“报告后追问保护”
- 当前更像“无法明确选工具时就自己回答”，而不是“无法明确选工具时继续交给 omni”
- 对“建议类/优先级类/改写类/管理动作类”问题缺少强路由规则

### 问题 B：信息不全时实体识别错误

#### 典型表现 1

用户输入：

`帮我查车辆风险报告`

系统把“风险”当成车辆标识去检索，回复未找到对应车辆。

#### 期望行为

应直接要求补充车牌号或车辆 ID，而不是把通用词当实体。

#### 根因判断

- 缺少通用词过滤
- 缺少意图和实体拆分
- 在信息不足时没有优先进入澄清模式

### 问题 C：驾驶员姓名 + 工号拼接解析失败

#### 典型表现

用户输入：

`请生成王强2202130驾驶员安全风险分析总结报告`

系统把 `王强2202130` 当作一个整体字符串查找，直接返回未找到。

#### 期望行为

应识别为：

- 姓名：王强
- 工号：2202130

然后进入正常检索或报告生成。

#### 根因判断

- 缺少姓名 / 数字串拆分
- 缺少检索前标准化处理
- 缺少“姓名 + 工号混合输入”模式规则

### 问题 D：短链路偶发卡在“正在生成...”

#### 表现

在新建会话、高频切换会话、快速重复测试时，部分请求停留在：

- 正在生成...
- 生成中

但迟迟没有最终结果，也不出现稳定的 `执行Agent` 落点。

#### 影响

- 会打断短对话对照测试
- 会导致用户误以为系统在工作，实际没有完成

#### 根因判断

- 可能是前端轮询状态丢失
- 也可能是后端任务完成后前端未正确收敛
- 需要结合接口日志进一步确认

## 通过样本

以下模式当前表现基本正常：

### 正常报告生成

- 指定线路名生成线路报告
- 指定车牌或车辆标识生成车辆报告
- 指定有效驾驶员工号生成驾驶员报告

### 信息不全时正确澄清

- 线路信息不全时，要求补充线路名称或编号
- 驾驶员信息不全时，要求补充姓名或工号

说明系统并非全局失效，而是主要在“上下文继承”和“复杂路由边界”上失稳。

## 关于“报告后追问”的定义

“报告后追问”指：

1. 用户先请求生成一个具体对象的报告
2. 系统已成功返回该报告
3. 用户继续围绕该报告内容发问

例如：

- 为什么动态风险排第一
- 给我两条管理层优先动作
- 哪一条适合本周先做
- 帮我改写成晨会话术

这类问题本质上依赖前文报告上下文，不应由 `router` 直接回答。

## 关于“全程都应由 omni 执行”的场景

这类场景通常不是“查报告/取结构化结果”，而是从首轮开始就属于业务分析和表达任务，例如：

- 根据 1 路当前风险，帮我写一段车队长晨会发言
- 结合王强风险情况，给出三条管理动作并排序
- 站在安全经理视角，判断本周先盯哪台车及原因

这类问题理论上应从首轮起就稳定交给 `omni`，`router` 只做分发。

当前已覆盖到部分“报告生成后继续分析”的场景，但对“首轮起就应全程 omni”的测试还不够系统，需要继续补专项样本。

## 建议的修复方向

### 1. 给 `router` 加强禁止直接答业务的边界

明确禁止 `router` 直接回答以下类别：

- 管理建议
- 优先级判断
- 行动排序
- 话术改写
- 总结归纳
- 基于既有报告的进一步分析

### 2. 增加“报告后追问”识别

如果当前会话中刚生成过结构化报告，后续问题又明显依赖该报告，则优先：

- 继承当前对象上下文
- 继续路由给 `omni/consult`

### 3. 强化实体标准化

至少补以下规则：

- 中文姓名 + 连续数字拆分
- “风险、报告、画像、分析”等通用词过滤
- 信息不足时优先澄清，不直接检索

### 4. 排查生成中卡死问题

建议核查：

- 前端轮询状态
- 会话任务完成回调
- 生成超时后的 UI 回收逻辑

## 当前结论摘要

- `router回复业务内容` 是本轮最关键、最稳定的问题
- 该问题在多轮报告后追问中复现稳定
- 短对话也存在问题，但更多表现为实体解析错误和生成卡死
- 第一层解释通常正常，但不能据此认为全链路稳定
- 系统当前最大风险点是：路由层和业务层边界不清，且会话上下文继承不稳
