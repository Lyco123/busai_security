# 测试与迭代指南

## 一、测试

### 1.1 通用原则

- 从真实目标出发：先明确系统是为谁解决什么问题，不要只测功能按钮本身。
- 用真实场景测试：测试输入要像真实用户、真实数据、真实约束，不要全是理想样例。
- 覆盖正常与异常：既要测标准路径，也要测信息缺失、表达模糊、边界值、冲突输入、误操作。
- 看结果，也看过程：不仅看最终有没有成功，还要看中间状态、提示、日志、数据落盘是否一致。
- 关注稳定性，不只看单次成功：同样的事重复做多次，观察波动、偶发错误、长链路退化。
- 区分表象问题和根因问题：界面文案错、提示词错、业务规则错、状态机错、存储错，不是一类问题。
- 能复现、能比较：测试要可重复，方便前后版本做横向对比。
- 先保正确，再谈聪明：系统可以不够「智能」，但不能不一致、不可预测、不可验证。

### 1.2 通用测试流程

1. 明确目标：系统成功的标准是什么，失败的标准是什么。
2. 划分场景：主流程、边界流程、异常流程、恢复流程。
3. 设计用例：覆盖完整信息、不完整信息、错误信息、冲突信息、高压重复输入。
4. 执行测试：按真实使用方式走，不替系统脑补。
5. 记录证据：输入、输出、状态、日志、保存结果、异常表现。
6. 归因分类：哪些是配置问题，哪些是实现问题，哪些是架构问题。
7. 修复后回归：用同一批核心用例重复验证，确认不是偶然通过。
8. 持续收敛：把高频问题沉淀成固定回归集。

### 1.3 判断系统好不好

- 正确性：结果对不对。
- 一致性：说的、做的、存的是否一致。
- 稳定性：多次执行是否波动小。
- 可恢复性：出错后能不能继续。
- 可引导性：用户不完美输入时，系统能不能把事情带到正确结果。
- 可解释性：出了问题，能不能知道为什么。

### 1.4 具体测试实践（规则管线示例）

**流程**

1. 先设计 5 条规则，尽量覆盖不同角色、不同需求和不同表达方式。
2. 每条规则先在测试环境完成配置，确认规则能成功保存。
3. 每条规则固定测试 3 个场景：常规场景、多轮对话场景、恶意场景。
4. 测试时不仅看最终回复，还看规则是否命中、是否进入正确链路、是否把恶意请求误判成缺参。
5. 以真实用户路径为准，优先看前端对话里的实际行为，不只看本地推断。
6. 以 metadata 和执行 agent 为准，区分「看起来答对了」和「实际上路由对了」。

**原则**

- 测试是「全量回归」，不是只挑通过的样例。
- 优化目标是通用能力，不是针对某个具体业务场景打补丁。
- 判断顺序要稳定：先看是否属于当前规则，再看是否越过安全边界，最后才看是否缺参。
- 恶意请求要优先拒绝，不能因为还缺信息就继续追问。
- 用户用自然语言已经给出的信息，应视为有效信息，不要求必须按字段名表达。
- 高命中规则应优先进入规则回复链路，不能让路由层随意自然语言代答。
- 每轮都用同一套场景重复测试，保证结果可比较、可复现。

### 1.5 十条通用 guideline

1. **先定义「什么算对」**：不是先跑测试，而是先明确成功标准、失败标准、关键约束和不可接受的行为。
2. **先测主路径，再测边界，再测对抗**：先验证最常见、最核心的使用链路，再覆盖异常输入、极端条件、恶意行为和多轮交互。
3. **用真实入口测真实行为**：尽量从用户实际会用的入口验证，而不是只测内部函数。系统对外怎么表现，才是第一真相。
4. **不只看结果，还要看过程**：既检查最终输出，也检查中间决策、调用链、状态流转、路由、日志或元数据，确认系统是「正确地得到正确结果」。
5. **一次只改变一个变量**：同一轮里不要同时改 prompt、逻辑、配置、数据集，不然无法定位根因。
6. **重复同一场景，观察稳定性**：单次通过不代表系统可靠。相同输入要重复跑，必要时在不同环境、模式、时序下复现。
7. **区分「表象」与「根因」**：不要只修复用户看到的症状，要判断问题来自数据、上下文、路由、状态、模型波动、配置还是环境。
8. **优先最小闭环修复**：发现问题后，先做最小但可验证的修复，再回归测试，避免一次性引入过多变化。
9. **让测试可复述**：每个测试都应能说明：输入是什么、预期是什么、实际发生了什么、证据在哪里、是否稳定复现。
10. **把测试当成持续循环**：测试不是收尾动作，而是「假设 → 验证 → 定位 → 修复 → 回归」的循环过程。

> 一句话总结：**测试任何系统，本质上不是「找 bug」，而是验证它在真实世界里是否稳定、可信、可恢复地完成目标。**

## 二、迭代

### 2.1 迭代流程

1. 先改 skill 或最小必要的路由逻辑，只做提示词工程和为管线一致性服务的有限重构。
2. 本地做静态校验，再提交、推远端，等线上环境更新（约 30 秒到 1 分钟）。
3. 用同一套测试集做全量回归，不只看回答文本，还看实际走的是哪个 agent、有没有误路由、有没有格式或数据问题。
4. 用前后两轮结果对比，判断问题是否真的收敛，而不是只看单次表现。
5. 记录每轮输入、输出、结论和改动，保证可复现。

### 2.2 迭代原则

- 发现问题后，只改与规则管线相关的提示词和路由提示，不直接按某个业务写死。
- 每次改动后都按同样格式 `commit`、`push`、部署，再做同样一轮全量回归。
- 每次尽量只验证一个变量，避免把 skill、route、AB、上下文污染混在一起。
- 同样的提示词要重复跑，必要时在不同 AB 模式下各跑一遍，观察是否稳定复现。
- 发现问题先定根因，再修最小闭环，不为了「压住现象」引入更大范围改动。
- 回归测试必须和之前保持同口径，否则结果不可比。
- 优化应优先针对通用机制，不要先靠特例补丁。

### 2.3 持续收敛

- 把高频问题沉淀成固定回归集。
- 人工判断要尽量转成明确标准，例如「是否误拒」「是否漏拒」「是否重复追问」「是否走错链路」。
- 好的测试不仅找 bug，还要帮助判断改动是否真的解决了 bug。
- 如果系统有多层，测试也要分层：输入层、路由层、执行层、输出层分别看。
